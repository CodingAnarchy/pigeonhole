# Changelog

All notable changes to Pigeonhole are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/). From 1.0, `pigeonhole`, `pigeonhole-arrow` and `phdb`'s interface follow semver (D282), and every 1.x release reads and writes file format 4 ([`FORMAT.md` §13](FORMAT.md#13-compatibility-promise)). Before 1.0, the format and the API could change in any release.

## [Unreleased]

## [1.0.1] - 2026-10-31

A correctness fix: snapshots are monotonic again. Upgrade recommended. The file format and the shared-memory layout are unchanged, so a 1.0.1 writer and 1.0.0 reader processes work together, and files move freely between 1.0.0 and 1.0.1.

### Fixed
- **A snapshot no longer sees fewer commits than an earlier one** (#1208, D300). While two shards reserved seqnos at once, the visible seqno could briefly go backwards: a later snapshot, in the writer process or in a reader process, could miss a commit an earlier snapshot had shown, including a writer's own acknowledged commit. No uncommitted data was ever visible. A shard's hold is now published under the seqno allocator's lock. Readers and the shared-memory layout are unchanged.

## [1.0.0] - 2026-10-30

Pigeonhole 1.0.0 is the first stable release of an embedded, single-file, wide-column store in Rust: BigTable's data model with SQLite's deployment model. It completes **Phase 4, hardening and 1.0**:
- **Promises:** a frozen file format with a written compatibility promise, and a semver-covered public API.
- **New tools:** the `phdb` command-line tool and Arrow export.
- **Engine:** transactions you can run and retry in one call, reader processes with their own row cache, automatic recovery in place, background workers for application-owned mode, and a load controller that sizes the shard threads.
- **Performance:** most of the contended gaps the Phase 3 gate found are closed.

The release gate ran on the reference machine, a Hetzner AX102, on 2026-10-30 at `main` [`790ae3a0`](https://github.com/CodingAnarchy/pigeonhole/commit/790ae3a0). It found no regression against the Phase 4 gate of 2026-10-29, and no FAIL that isn't a known, accepted gap. The gaps 1.0 ships with are listed in [`docs/status.md`](docs/status.md).

### Upgrading from 0.3.x
- **Back up before the first writable open.** 1.0 writes **file format 4**, the format every 1.x release reads and writes (D269). A writable open upgrades a 0.x file in place, and then 0.3.x (and any earlier release) refuses it with `UnsupportedFormat`. The upgrade is one-way: take a `backup` (or copy the closed file) first if you may need to roll back. A read-only open never upgrades (reader processes, and `read_only_fallback`). 1.0 opens every file written by 0.1.0 or later.
- **Upgrade reader processes together with the writer.** The shared-memory layout is version 6 (`ShmLayoutVersion::CURRENT`; its last two steps are the shared row-epoch table, D281, and decided cross-shard seqnos held in the header's `cross_held` word, D278). A reader from 0.3.x can't attach to a 1.0 writer, nor the reverse (`ShmVersionMismatch`). Stop the readers, upgrade, start them again. The shared-memory layout is outside the 1.x promises, so do this on every upgrade.
- **Breaking API changes, made before the freeze** (ICR 0071, D282 and ICR 0073, ICR 0060):
  - **`#[non_exhaustive]`:** `Value`, `Condition`, `ValueFilter`, `Compaction`, `Priority`, `Recovery`, `Durability` and `FailureCause` are `#[non_exhaustive]`: add a `_` arm to a `match` on any of them. `CommitInfo` and `CellEntry` can no longer be built with a struct literal.
  - **Own types:** `pigeonhole` defines its own `Durability`, `Failure`, `FailureCause`, `RowCacheStats`, `MergeError` and `MergeOperator` instead of re-exporting the engine's. A merge operator builds its error with `MergeError::new(operator, message)`. The public `From` conversions from engine types are gone.
  - **Transaction futures:** `Transaction::commit_async` and `commit_with_async` return `nonblocking::TransactionCommitFuture`. Code that only awaits them is unaffected.
  - **Exact pins:** `pigeonhole` pins its internal crates exactly (`=`). Depend on `pigeonhole`, not on `pigeonhole-engine` and the other internal crates.
  - **The `tokio` feature is gone** (owner, 2026-10-28). It gated no code and only turned on `async`, which is on by default. Drop `features = ["tokio"]` from your `Cargo.toml`, or name `async`.
  - **Tuning hooks moved out of the API (ICR 0085).**
    - `Options::commit_spin`, `shard_spin`, `tablet_changes` and `tablet_packing` are gone from the public API, along with the hidden test hooks. They now exist only behind a test feature that applications don't use. Drop these calls: the spin windows keep their defaults (50 and 200 µs; the shard spin is 1 ms under `CpuProfile::Server`), and tablet changes and packing are always on.
    - `Options::adaptive_shard_threads` stays public (#1082); see the behaviour changes below.
    - `Options::allow_unregistered_merge_operators` is removed; use `read_only_fallback`.
    - The library no longer reads the `PIGEONHOLE_IO` and `PIGEONHOLE_DIRECT` test variables: set `io_backend` and `direct_io` instead.
  - **Renames and one-spelling fixes (ICR 0086):**
    - **Compression:** `Family::lz4()`, `zstd(level)` and `uncompressed()` are now `Family::compression(Compression::Lz4 | Compression::Zstd(level) | Compression::None)`.
    - **Column limit:** `Scan::columns_per_row(n)` is now `Scan::column_limit(n)`.
    - **`Row::entry(i)`** returns a `CellEntry` (`.family`, `.qualifier`, `.cell`) instead of a tuple.
    - **`async_sync_reads`:** `Pigeonhole::async_sync_reads()` is gone; read `engine_metrics().async_sync_reads`.
    - **`repr(C)`:** `Failure` and `Recovery` are no longer `#[repr(C)]`.
  - **One application-owned open (ICR 0088):** `Pigeonhole::open_application_owned` returns an `AppOwned { db, shards, workers }`, and `open_application_owned_with` is gone. Write `let AppOwned { db, shards, .. } = Pigeonhole::open_application_owned(path, options)?;`.
  - **Metrics (ICR 0087):** the metrics structs keep the counters an application acts on. The engine's mechanism counters are gone from them: shard parks and wakes, WAL unpin and rollover counts, visibility waits, cross-shard refusals by reason and share waits, file growth ahead, the reader view lag, `IoRings::pooled`, and the deprecated `refused_below_floor` and `refused_move_raise`. `WalFile::checkpoint` and `end` are a `WalPosition { epoch, offset }`.
- **Behaviour changes to know:**
  - **Shard threads:** engine-owned mode now sizes its shard threads by load (D289, #1015, #1082). It starts a thread per shard, gathers a light load's shards onto fewer threads, and spreads them out again under load. `Options::adaptive_shard_threads(false)` keeps 0.3's thread per shard; setting `Options::shard_threads(k)` also turns the controller off.
  - **Row cache and point gets:** point gets, including a transaction's and a snapshot's, are now served from the row cache (D290). By default they don't fill it; row reads still do (D290 as amended, #1059, #1158).
  - **Per-cell conflicts:** a transaction's `get` conflicts per cell, not per row (D275), so fewer transactions fail with `Conflict`. A transaction that writes nothing commits at once and never conflicts.
  - **Reader row cache:** each reader process now has a 64 MiB row cache by default (`ReaderOptions::row_cache`), so N reader processes use up to N × 64 MiB. `row_cache(0)` turns it off.
  - **Flush and compaction threads** scale with the physical cores (a quarter of them by default, no longer capped at four). They take work from one shared queue, flushes first.
  - **`shrink` while a snapshot or backup is held** gives back less, and never grows the file (#1099). Shrink again after the snapshot is dropped to give back the rest.
  - **Reader processes on a reused inode:** opening a database whose file reuses a deleted database's inode fails with `NoWriter`, not `Corruption`, until that database's writer runs (#1133).
  - **Under `auto_recover`,** a commit refused during or after a recovery gets `Busy` or `SnapshotExpired` (a transaction, which `transact` retries) once the database has recovered, and `Closed` while the recovery runs or after a give-up. It no longer gets `Io` (#925, #966).
- **Minimum Rust version:** 1.96. From 1.0, a 1.x minor release may raise it and a patch release never does (D283).

### Added
- **Automatic recovery in place** (D265, ICR 0050, #620): `Options::auto_recover(Recovery::Io | Recovery::Any)` starts a supervisor thread per writer handle that, on a failure the setting covers, closes the failed engine keeping its writer lock, reopens the same path on it and swaps the new engine in behind every `Pigeonhole`, table and batch, which keep working. Operations arriving during the pause wait up to `write_stall_timeout` for the swap, then get `Busy` (not committed, retry); a commit in flight at the failure comes back as `Busy` too; snapshots, transactions, scans and row iterators from before fail with `SnapshotExpired`. Three recoveries per ten minutes with a backoff of 0, 1 and 4 s; past that, or on a reopen that fails for good, the handle stays failed as before. `Pigeonhole::recovery_stats()` reports the generation, the recoveries, a give-up and the last failure. Off by default; refused in application-owned mode. The recovery guide has an "Automatic recovery" section. The public model check has an arm for it: injected read and write errors with the option on, every recovery checked by reading the store back against the commits from before the failure (`tests/model.rs`).
- FORMAT.md §13: the 1.x file compatibility promise (D269, #496). Every 1.x build opens every file written by 0.1.0 or later; a newer 1.x build's file opens unless it uses a feature this build lacks (then `UnsupportedFeature`, or read-only with `read_only_fallback`). The section also says where each structure has room for later features, and how each tracked post-1.0 feature fits format 4. The shared-memory layout stays outside the promise.
- The guide's [file format and upgrades](docs/guide/concepts.md#file-format-and-upgrades) note: upgrading a file is one-way, so back up before the first writable open with a new release.
- `Options::read_only_fallback` (ICR 0059, #496). A writer open of a database this build can't write opens read-only instead of failing. That covers a feature from a newer version that older ones may only read (otherwise `UnsupportedFeature`), and a family naming an unregistered merge operator (otherwise `UnknownMergeOperator`). Such an open writes nothing to the database's files:
  - no format upgrade, flush, compaction or clean-close mark;
  - the write-ahead log is replayed into memory, and an open whose log doesn't fit `memtable_budget` fails with `ReadOnly`;
  - `flush`, `compact` and `shrink` fail with `ReadOnly`, as writes do.
- `DatabaseInfo::features` (a new `FileFeatures` struct) and `DatabaseInfo::read_only`. `phdb info` shows both.
- `ErrorCode::UnsupportedFeature` (30): the file uses a feature from a newer version, a stored value this build doesn't know. The message names it (#496, ICR 0058). Unknown key kinds, value tags, block and filter kinds, family settings (kind, compaction style, cache priority, compression), compression codecs and WAL record types used to be reported as `Corruption`, sending users to their backups for files that were intact.
- `pigeonhole-arrow`: `scan_to_arrow` exports a scan as Arrow `RecordBatch`es, one Arrow row per cell (`row`, `family`, `qualifier`, `ts`, `value`, `value_type`), through a streaming `RecordBatchReader` (#691). Everything the scan selects passes through, so the batches hold a plain scan's cells. `ArrowOptions` adds typed `value_i64`/`value_f64` columns, UTF-8 keys, a row dictionary, raw `u64` timestamps and the batch limits. Each key and value is copied once, with no allocation per cell. The crate pins arrow-rs 60 and re-exports it. New guide page: `docs/guide/arrow.md`.
- `pigeonhole-bench` example `arrowexport`: Arrow export throughput (GB/s of key, qualifier and value bytes) beside a plain lending scan of the same warm table, for narrow, wide, large-value and counter shapes (#691). The guide's Arrow page reports a run.
- `pigeonhole-arrow` feature `ffi`: `ArrowScan::into_ffi_stream` hands an owned export over as an Arrow C stream (`FFI_ArrowArrayStream`), for consumers on another arrow-rs major or in another language (#691).
- `phdb dump --format arrow --table T`: one table as an Arrow IPC stream, in the Arrow export's schema with `value_i64` and `value_f64`, every retained version at one snapshot (#691). A cell an Arrow batch can't hold, such as a timestamp above `i64::MAX`, fails the dump with status 6 (`Unsupported`); any other Arrow writer failure is status 1 (`Export`). A failed dump leaves a prefix on standard output: check the status. CI reads such a dump with Polars.
- `Scan::into_owned`: a scan that holds its table instead of borrowing it (ICR 0052). Its `RowIter` (and its `RowStream`, with the `async` feature) is `Send + 'static`, so it can move to another thread or into a consumer that keeps it, such as the Arrow export coming in `pigeonhole-arrow` (#691). It keeps the database open as a clone of the table handle would.
- `pigeonhole::check`: an offline integrity check of a database no writer has open (ICR 0048). It checks both superblock slots, the manifest, the extents, every SST block with its checksum forced, every blob record, and the WAL sidecars a crash left, chained as replay would read them. Damage comes back as findings (`CheckReport`, `Finding`, `Structure`, `Severity`), with a map of the file's regions. It replays nothing and writes nothing. `CheckOptions::deep` also reads every blob pointer through.
- `phdb backup`: a consistent single-file copy at a durable snapshot (`--latest` copies everything committed). `--check` checks the copy afterwards (#692).
- `phdb compact`: a full compaction with progress on standard error. `--shrink` then releases free space at the file's end (#692).
- `phdb check`: an offline integrity check from the command line. It covers superblocks, the manifest, extents, every SST block, every blob record and a crashed database's WAL, and exits 3 on damage. `--deep` reads every separated value through. `--map` lists the file's regions. `--online` reads every table through a reader process while a writer runs (#692).
- `phdb dump`: exports every cell, with all retained versions, at one snapshot, as JSONL (the default) or CSV. `--table`, `--prefix` and `--durable` narrow it. A writer may be running. `phdb load` reads the JSONL back into a database, creating its tables and families with their stored options and writing every cell at its timestamp (#692).
- `Pigeonhole::info` and `PigeonholeReader::info`: what a database holds and how it is stored. They give the format version, the file and free bytes, and per table its tablets, its families' stored options, and their SSTs per level and blob files (`DatabaseInfo`, `TableInfo`, `FamilyInfo`, `FamilyStorage`, `LevelInfo`, `Compression`; ICR 0047).
- `Table::family_info`, `ReadTable::family_info` and `ReadTable::families`: a family's stored options read back. `FamilyInfo::family` is a `Family` that defines an identical family elsewhere (ICR 0047).
- The `phdb` command-line tool (`pigeonhole-cli`, #692), starting with `phdb info`. It offers `table`, `json`, `jsonl` and `csv` output, stable JSON for programs (`"phdb": 1`) and documented exit statuses. It opens as a reader process while a writer runs, and otherwise as the writer for the command. See [the CLI guide](docs/guide/cli.md).
- `phdb shell`: a small command language over the public API, not SQL. It covers `get`, `scan` (ranges, prefixes, family, qualifier and value filters, versions, time ranges, limits), `put` (typed and timestamped), `incr`, `delete`, `create`, named snapshots and meta commands (`\tables`, `\schema`, `\info`, `\metrics`, `\health`, `\format`, `\timing`). Commands come from `-c`, a script, a pipe, or an interactive terminal. It is read-only while a writer process runs (#692).
- `RowMutation::put_f64_at` and `WriteBatch::put_f64_at`: a typed `f64` at an explicit timestamp, like `put_i64_at` (ICR 0051).
- `PigeonholeReader::backup` and `backup_durable`: a consistent single-file copy from a reader process while the writer runs (ICR 0049). The reader's snapshot pins the writer's memtables for the copy's length, so on a write-heavy database the writer's commits can wait meanwhile. A writer restart mid-copy fails it with `SnapshotExpired`. `phdb backup` uses it while an application has the database open (#692).
- `Options::reader_slots`: how many reader processes can attach at once (default 128, up to 65,536; ICR 0055). One more `open_reader` fails with `NoReaderSlot` at once.
- `engine_metrics()` reports reader processes: `reader_slots_active` out of `reader_slots`, `reader_slots_reclaimed`, and how far the oldest reader snapshot lags, as `reader_pin_view_lag` and `reader_pin_seqno_lag`. A lag that keeps growing is a reader holding a snapshot, which eventually stalls the writer's commits into `Busy` (#693).
- A guide page on reader processes (`docs/guide/readers.md`): what readers see, crashes and restarts on either side, long-held snapshots, the limits and the requirements. It includes Windows readers in another session, which attach through a shared `shm_dir`.
- `Pigeonhole::transact` and `RetryPolicy` (#694, ICR 0060): run a transaction and commit it, retrying `Conflict`, a snapshot a recovery expired, and optionally `Busy`, with exponential backoff and full jitter, up to an attempt cap or deadline. The closure may return the application's own error type (`E: From<pigeonhole::Error>`) to give up without committing. `RetryPolicy::retries` and `delay` let async code drive the same policy with its own timer.
- `EngineMetrics::transactions`, `transaction_conflicts` and `transaction_retries` (#694, ICR 0061): transaction outcomes and retries since open, across automatic recoveries.
- `Transaction::get_row` (#694, ICR 0062): read a row at the transaction's snapshot. Each family it covers counts as read, so a commit touching any column of those families, or creating the row, makes the transaction conflict.
- The `RowMutation` write ops that `Transaction` lacked (#694, ICR 0062): `put_at`, `put_i64`, `put_i64_at`, `put_f64`, `put_f64_at`, `incr`, `incr_at`, `merge`, `delete_cell`, `delete_family`, `delete_row`.
- The guide's [Transactions](docs/guide/transactions.md) page (#694, D272): `transact` and retries, the (row, family) conflict granularity, the isolation level (serializable over what a transaction reads; lost update and write skew prevented), read-only transactions, the cost model, and the errors.
- `RowCacheStats::write_throughs`: cached rows a commit moved forward.
- `phdb-bench app-owned --engine-owned`: the application-owned row's workload (the same stream, ~20% cross-shard batches, 16 commits in flight per shard's thread) on engine-owned shards, its D280 comparator (#816, #710).
- `phdb-bench --riders` on RocksDB: a `Checkpoint` and then a `BackupEngine` backup 2 s into the measured phase, timed, with each side's backup bytes, beside Pigeonhole's durable backup (D280, #715). The gate's contended step runs both.
- `pigeonhole-bench` `--cache-model per-store|total`: `total` holds every store to the same read-cache memory (#759). Pigeonhole's block and row caches share `--cache`, and SQLite's per-connection page caches split it across the connections, where before each of SQLite's connections (one per client thread) got the whole budget. `per-store`, the default, keeps today's sizes so earlier results stay comparable.
- `pigeonhole-bench --offered-rate R` now also paces client runs (before, only the placement check): a run's measured operations are offered at about R per second in all, each client paced to R / clients, so latency is the store's service time at that load rather than at its maximum (#759: read p99 at equal offered load). The JSON record carries `detail.offered_rate`.
- `Options::adaptive_shard_threads`: a load controller sizes the shard threads to the load, up to one per shard (D289). It is on by default (#1015).
- `Options::cpu_profile(CpuProfile)` (D289, ICR 0081). `CpuProfile::Embedded` (the default) leaves CPU for an application in the same process. `CpuProfile::Server` is for a database whose clients are elsewhere, such as another container, and gives flush and compaction half the cores.
- `Options::shard_threads(k)` runs the shards on `k` threads rather than one each (D289, ICR 0079, #760). Shard `i` runs on thread `i % k`, which takes its shards' turns one after another and parks only when all of them are idle. Fewer, busier threads sleep less, so a commit waits less often for its shard's thread to be woken. The default, 0, keeps one thread per shard.
- `CrossShardMetrics::share_waits` and `share_wait_nanos`: single-shard commits held back behind an undecided cross-shard commit's rows, and for how long (ICR 0046).
- **Background workers for application-owned mode** (D284, ICR 0078, #816): `Options::background_workers(n)` with `Pigeonhole::open_application_owned`, which returns an `AppOwned { db, shards, workers }`. Flush and compaction then run on `BackgroundWorker`s, which you drive from threads you choose as you drive the shards, rather than in slices on the shards that hold up the commits queued behind them. `AppOwned::spawn_background_threads` gives each worker a thread of its own instead. A close never waits for a worker to be driven: it takes the workers' tasks back to the shards. Engine-owned `open` ignores the option (`compaction_cores` instead). The async guide's "Background workers" section shows the loop.
- New counters: `EngineMetrics::compactions_reclaimed`, and `background_fallback_take_backs` and `background_room_take_backs`, the tasks shards took back from workers nobody drove. Both take-back counters stay 0 while the workers are driven.
- `ErrorCode::NoWriter` (29): a reader process found no running writer to attach to (ICR 0057, #844). `open_reader` with no writer running returns it, as does a reader's next read when the writer generation it must re-attach to is gone (on Windows, a writer that opened and closed meanwhile). Both used to fail with an untyped `Io`. Open the reader again once a writer runs.
- `EngineMetrics::room_stalls`, `room_stall_nanos`, `pacing_stalls` and `pacing_stall_nanos` count the two kinds of write stall apart: waits for memtable arena room (arena pressure) and L0 pacing while compaction catches up (compaction debt). `write_stalls` and `write_stall_nanos` stay, as their sum (#724, ICR 0054). The shell's `\metrics` lists both kinds.
- `pigeonhole-io`: `FaultPlan::fail_on` fails the next write or sync of a file whose name contains a given component, once, with nothing written; the simulator clears it as it fires and `SimVfs::scheduled_fired` counts the firings (#880). The public model check's recovery arm uses it to force one WAL failure per seed, so every seed exercises a recovery whatever the random faults hit: where those land depends on the threads' interleaving (one simulator RNG serves every thread's I/O), not only on the seed, and a seed's faults may never hit a WAL write. The `FaultPlan` doc says so.
- `pigeonhole-engine`: `Error::ShardFailed`, a commit refused before anything of it was logged by a shard whose WAL stream failed earlier (it was `Error::Io`; the message is unchanged) (#925).
- **Reader processes have a row cache** (D281, ICR 0072): `ReaderOptions::row_cache(bytes)`, 64 MiB by default as the writer's (0 turns it off), with `row_cache_max_row` and `row_cache_family`, and `PigeonholeReader::row_cache_stats()`. Hot rows read in a reader process cost about what they cost in the writer process; results are identical to uncached reads. Each reader process has its own cache, so N reader processes use up to N × 64 MiB by default. It needs the writer's row cache on (the default): a writer opened with `Options::row_cache(0)` gives its readers none.
- `pigeonhole-engine`: `Snapshot::table(id)`, the table as the snapshot's catalog knew it, borrowed (ICR 0068, #927, #892).
- `pigeonhole`: `IoRings::attach_failures` and `IoRings::inline` count refused ring attaches and the operations run inline meanwhile (ICR 0070, #938). `pigeonhole-io`'s `RingStats` has the same fields.
- A reader process's async latest reads (`get_async` and the async row read without a snapshot) go through its row cache, as its sync reads do (#946, D281).
- `pigeonhole_io::File::submit_reads_ahead`: submits reads nothing waits on yet (a scan's readahead) as one batch. The default submits each read in turn; a backend may hand the batch to the kernel at once (ICR 0077, #977).
- Application-owned mode can run flush and compaction on background workers the application drives from its own threads (D284, #816): `EngineOptions::background_workers` and `Engine::open_application_owned_with`, which returns the engine, the shards and the workers (`BackgroundWorker`: `run_once`, `wait`, `waker`, `set_wakeup`, `next_deadline`, `closed`). No threads are started (D40). A worker's I/O runs inline on the thread that drives it, so the application may stop driving one at any time: the close takes its work back without waiting for it, and a shard waiting for memtable room takes back a flush the worker is not running. The default stays 0 workers (flush and compaction on the shards, as before). `pigeonhole_io::inline_io` is the I/O scope the workers run in.
- `Metrics::compactions_reclaimed` and `Metrics::background_take_backs`: compactions dropped because their worker was dropped or the engine closed (they compact again), and tasks a shard took back because no worker was driven or a room wait needed the flush.
- `pigeonhole-engine`: `Engine::table_by_id`, a table's current catalog entry by id (ICR 0092). `pigeonhole`'s row reads use it to find their table's entry without hashing its name on every read.

### Changed
- **Cross-shard commits on a hot row no longer wait for each other** (D271, #816, #854). Every seqno and default timestamp now comes from one per-database allocator, so a later commit can never get an earlier default timestamp on any shard. A cross-shard commit that only writes rows another commit is still deciding no longer waits for that decision (0.3.0 refused and retried it, D267 queued it behind): both decide independently, at one two-phase round each. Commits that read keep the optimistic checks: one reading a row another commit is still writing is retried once that commit decides. Locally, application-owned inline driving at the small scale went from about 170K to 460K commits/s with one round per cross-shard commit.
- New counters (ICR 0056): `CrossShardMetrics::max_attempts_blind` and `max_attempts_reading`, the most attempts one committed cross-shard commit took. Only committed commits count, so read them with the `Busy` failures. `chained` and `wounds` exist and are always 0 (D271). (The curated metrics, ICR 0087, later took all four out of the public `CrossShardMetrics`.)
- **A cross-shard transaction that can only fail no longer retries first** (D276, #708). A commit refused because it overlapped another commit's undecided write is now told to fail with `Conflict` as soon as that commit writes a row it read, instead of waiting, running another two-phase round and failing validation there. Only commits whose retry would fail validation are failed. New counter (ICR 0066): `CrossShardMetrics::failed_fast`.
- New gauges (D271, ICR 0064): `EngineMetrics::default_ts_lead_micros` and `max_default_ts_lead_micros`, how far default timestamps run ahead of the clock. They lead only when one shard commits more than one group a microsecond. (The curated metrics, ICR 0087, later took both out of the public `EngineMetrics`.)
- **Format version 4**, the format 1.x is frozen at (D269, #496). It reserves room to grow without another version bump:
  - feature bits in the superblock (compat, ro_compat, incompat), in the SST footer and in the WAL segment header, which grows to 128 bytes;
  - an extension area in the superblock, which every root commit carries forward unchanged;
  - must-understand (1 to 127) and skippable (128 to 255) manifest edit tags.

  No feature bit is defined yet. A writable open upgrades an older file as before: both superblock pages carry version 4 before any WAL write, and builds before format 4 then refuse the file with `UnsupportedFormat`. This build still reads files of versions 1 to 3. A file using a feature this build does not know is refused with `UnsupportedFeature`, or for a read-only-compatible feature, refused for writing only. FORMAT §8.2 states what a compat feature's data may rely on when a build that does not know the feature writes.

- `DatabaseInfo::format_version` is the file's version: a read-only open no longer reports this build's.
- Creating a family that names an unregistered merge operator is refused whatever the options.
- The writer judges whether a reader process is alive by a byte-range lock the reader holds on the database file for its slot, not by its process id (#693). A reader in another PID namespace (another container sharing the volume and shared memory) is no longer taken for dead, losing its slot and getting `SnapshotExpired` over and over, so the writer and its readers no longer need to share a PID namespace. A reader that dies while claiming a slot no longer leaks it until the next writer generation. This changes the shared-memory layout: a writer and readers from earlier releases can't attach to each other's shared memory (`ShmVersionMismatch`).
- A process forked from a reader process can no longer free the parent's reader slot or clear its pins by dropping its copy of the reader; in the child, dropping or closing the copy releases nothing, a new snapshot fails with `Unsupported`, and reads through the parent's snapshots fail with `SnapshotExpired` (#693). Only `fork(3)` is detected (`_Fork`, `vfork` and raw `clone` skip fork handlers).
- With `Options::auto_recover`, a transaction whose commit the failed engine refuses during a recovery now gets `SnapshotExpired` rather than `Busy` (#694, ICR 0060, refining ICR 0050). It's still "not committed", and `transact` retries it by default.
- `Transaction::commit_async` and `commit_with_async` return `nonblocking::TransactionCommitFuture` instead of `CommitFuture` (#694, ICR 0060): a future of the same output that also counts the outcome in the transaction metrics. Code that only awaits it is unaffected.
- A transaction that writes nothing now commits at once and never fails with `Conflict` (#694, ICR 0060). Its reads all come from one snapshot, so it's serializable there. It used to be validated like a writing transaction, which could abort it for nothing. Its `CommitInfo` names the snapshot's seqno and `Durability::None`, because it wrote nothing. A read-only transaction at `Sync` no longer makes what it read durable as a side effect: use `durable_snapshot` for reads that must be durable.
- **Breaking (before the 1.0 API freeze, ICR 0071):** `Value`, `Condition`, `ValueFilter`, `Compaction`, `Priority` and `Recovery` are `#[non_exhaustive]`, as are the output structs `CommitInfo` and `CellEntry`. A `match` on one of the enums outside the crate needs a wildcard arm, and the two structs can no longer be built with a struct literal. After 1.0, a new value type, condition, filter, compaction style, cache priority, recovery level or commit field is then a minor release, not a major one.
- **Breaking (before the 1.0 API freeze, D282, ICR 0073):** `pigeonhole` no longer re-exports internal crates' types; it defines its own.
  - **Own types:** `Durability`, `Failure`, `FailureCause`, `RowCacheStats`, `MergeError` and the `MergeOperator` trait are now `pigeonhole`'s own (same names, variants and fields), and all but the trait are `#[non_exhaustive]`.
  - **What callers change:** a `match` on `Durability` or `FailureCause` needs a `_` arm. A merge operator builds its error with `MergeError::new(operator, message)`. Code that passed these values to or from `pigeonhole-engine` or `pigeonhole-format` directly must convert.
  - **Conversions removed:** the public `From` conversions from engine types (`CommitInfo`, `EngineMetrics`, `CheckReport`, `FamilyInfo`, `DatabaseInfo`) are gone.
  - **Exact pins:** `pigeonhole` pins its internal crates exactly (`=`).
- The guide's [versions and compatibility](docs/guide/concepts.md#versions-and-compatibility) section and the READMEs state the semver policy from 1.0.0:
  - `pigeonhole`, `pigeonhole-arrow` and `phdb`'s interface follow semver;
  - the internal `pigeonhole-*` crates make no stability promise;
  - a 1.x minor may raise the minimum Rust version, and a patch never does (D283).
- **The row cache now serves transactions and snapshot reads** (D290, #708). Point gets in a transaction or at a snapshot are answered from the writer's row cache when the cached row is current at their read point. Before, they always read the memtables and SSTs.
- **A commit that overwrites cells of a cached row keeps it cached** at the new version, instead of leaving it to miss until it is read twice more.
- **Point gets are served from cached rows but don't fill the cache;** row reads fill it, as before (D290 as amended after the A/B on #1059: storing a whole family row for one cell cost write-heavy point-get workloads more at the tail than it saved: in the box A/B, transfer's p99 fell from 224 to 181 µs without it, ycsb-f gained 3.6% throughput, and sparse-wide get p99 fell from 18 to 10 µs).
- Transactions and conditional writes that read a hot row validate faster: validation reads each column's newest version only, instead of every buffered version, wherever every version there carries a default timestamp (D273, #708). A memtable holding an explicitly timestamped cell, or rebuilt by recovery, is still checked in full.
- An async get or row read as of now (`get_async`, `read_async`) runs at the call first, as the blocking call does. A memtable or cache hit is read there, as of the call, and the future only hands the result over on its first poll. Such a future no longer holds a reference to the engine, the current view or a copy of the key. Concurrent async readers used to write those shared reference counts on every read, and ran at about 0.4× the blocking reads' throughput at 16 clients (#709). A read that misses the cache, and a read at a snapshot, work as before.
- A row read no longer clones the catalog's reference count to look up its table (#709).
- An async read (`read_async`, `get_async`, async scans) that misses the block cache but finds the block in the OS page cache now reads it in place and carries on, as a synchronous read does. Previously, it abandoned the read, fetched the block, and ran the whole read again for every block it missed. A read that must wait on the device still returns a future, and that future resumes the read already submitted rather than submitting it again. Results are unchanged. On the benchmark's read-only YCSB C with 16 client threads keeping 16 reads each in flight, async throughput rose 27% (1.93M to 2.46M operations per second), and async CPU per operation fell from 8.1 to 6.2 µs; synchronous reads are unchanged (#709).
- A read that misses the block cache, sync or async, no longer allocates and zero-fills a new buffer for the block's bytes as read from the file each time. It reuses one of a few per-thread buffers that the read overwrites entirely. What the block cache keeps is charged exactly as before. Results are unchanged (#709).
- Scan readahead ramps up (#712). A scan cursor reads ahead only after it has moved through two blocks past its seek, 2 blocks first, then 4, 8 and 16. Before, the first block-cache miss fetched 16 blocks. Short scans, which read a few rows past their seek, no longer fetch, verify and decompress blocks they never reach.
- Counter families: a flush now combines a memtable's increments of each counter into one operand, as compaction already did (D287, #713). Before, every increment reached the first level as its own entry, and reading a hot counter folded every increment since its last compaction: on the reference machine, counter reads over 1 ms spent about two-thirds of their time on those entries. Reads return the same values; the files the flush writes are smaller.
- Flush and compaction threads now scale with the physical cores (a quarter of them by default), no longer stopping at four (D289, ICR 0081).
- A cross-shard commit takes one two-phase round instead of two (D263): its PREPAREs carry a provisional id, and the seqno and timestamp it applies at are picked when it is decided and held only until every participant applied it. Single-shard commits no longer wait for a cross-shard commit's PREPARE round to be visible (on the reference machine, single-shard p50 37 → 24 µs buffered and 193 → 104 µs at `GroupSync` with half the commits across shards, and +7–18% throughput on the cross-shard rows). While a cross-shard commit is undecided, a single-shard commit that writes one of its rows, or reads one of them in a transaction, waits for the decision, and another cross-shard commit on those rows is retried (D249), so each cell's versions stay in seqno order. Cross-shard p99.9 rises on contended workloads (about 1.5–2× on the reference machine's contended rows; p50 unchanged).
- The WAL has a new DECISION record (ICR 0046), part of file format 4. **0.2.x and 0.3.x cannot open a database this version has opened for writing:** they fail with `ErrorCode::UnsupportedFormat`. This version opens 0.1.x–0.3.x files and replays their WALs; opening one for writing upgrades it first.
- A cross-shard commit's WAL records are checkpointed once every shard holding its writes has flushed past it, read off each shard's published flushed-through seqno, instead of from per-share flush reports between the shards (D266). A flush install no longer reports each cross-shard share it covers, and coordinators no longer settle commits one by one: on 16 shards that work held a flush's shard turn for about 6 ms. A cold memtable on a shard now holds back the checkpoints of every cross-shard commit that shard took part in until the WAL pin flushes it, as it already held back that shard's own commits.
- A packing move no longer hands a tablet to a shard a skew move has just claimed, and a tablet change that waits on a compaction no longer holds its target shards off other changes while it waits (D270).
- `pigeonhole`, `pigeonhole-engine`: a transaction's `get` now conflicts per cell (D275, #917). A commit that writes another column of the same family in that row no longer makes it conflict; one that writes the cell, or deletes its family or row, still does. `get_row` still conflicts with any write to the families it read. Concurrent read-modify-writes of different fields of a hot row now commit side by side.
- **The shared-memory layout is version 6 in this release**: version 5 moved the row caches' write watermarks into the region (D281), and version 6 added the fields for #955's cross-shard answers (D278). The region grows by 2 MiB at the defaults (`memtable_budget × shards` plus about 12 MiB). **Upgrade reader processes together with the writer:** a reader from an earlier release can't attach to a writer from this one, nor the reverse (`ShmVersionMismatch`).
- `pigeonhole`: reads at a snapshot (row reads, scans, `get_at`, a transaction's reads) resolve and name families from the catalog as of the snapshot (#927, #892).
- Reader processes read overwritten rows as fast as the writer process (#930, #397, D277). The writer's index of where a column's superseded memtable versions end (D194) lived in its own memory, so reader processes stepped over every superseded version: a reader read the 16 hottest rows of ycsb-a at a third of the writer's speed (15.1 against 4.7 µs per read, row cache off). The writer now stores that offset in each memtable entry, in shared memory, and readers jump by it. This changes the shared-memory layout: **upgrade reader processes together with the writer.** Readers from earlier releases can't attach to this writer's shared memory, nor the reverse (`ShmVersionMismatch`); the new writer rebuilds it once every older process has closed. Each memtable entry takes 4 more bytes of arena, and the writer no longer keeps the separate index (an eighth of its arenas' size in process memory).
- **`transact` no longer sleeps for a retry pause below 100 µs** (ICR 0060, #932). It yields the core until the pause has passed, since Linux stretches every short sleep by the thread's timer slack (50 µs by default), which more than doubled the short pauses. On the reference machine, transfer's p99 fell from 464 to 190 µs at `Buffered` and from 1,282 to 688 µs at the default durability, with 2.6% and 3.5% more throughput. Longer pauses still sleep, and `RetryPolicy`'s pauses are unchanged.
- **A cross-shard commit is answered by the shard that applies it last** (D278, ICR 0074, #932). That shard makes the commit visible and answers the caller itself, instead of telling the coordinating shard, which then did both. The client's answer and every later commit's visibility skip one hand-off between shards. The hold on a decided commit moved from the coordinator's watermark into a new shared-memory word, so the shared-memory layout changes: reader processes must run the same build as the writer, as with every layout change.
- `backup` and `backup_durable` copy the database's SST and blob files byte for byte instead of re-merging every entry (#715). A backup now takes about as long as copying the live data, and the copy is about the size of the live data: it no longer carries the source's free space, a block grown ahead of need, or free space from its own temporary files (63 MB of data made a 192–256 MB copy before, 66.5 MB now). The copy keeps the source's level shape and holds a blob file only if the snapshot references a value in it. The file format is unchanged.
- **A `Buffered` cross-shard commit decides sooner** (D279, #932). A participant now votes as soon as its share's record is in its log, rather than after it has written the record and finished its turn, so the coordinating shard writes its decision meanwhile. A participant whose write then fails can no longer turn the commit into a clean failure: the commit returns `OutcomeUnknown`, as any commit does when its shard fails after logging it. Other durability levels are unchanged.
- io_uring backend: a scan's readahead goes to the kernel as one batch, each read run by a kernel worker thread, rather than one system call per block on the scanning thread. Concurrent scans no longer queue behind each other's page-cache copies on the shared ring. The kernel's worker threads per submitting thread are capped at 4 (#974, #977).
- Engine-owned compaction threads now take flushes and compactions from one queue, flushes first, instead of each shard's tasks going round-robin to the threads; timers stay on their shards.
- **A `Buffered` cross-shard commit finishes sooner** (D286, #708). The coordinating shard now tells the other shards to apply as soon as it decides, while it writes its decision, rather than after. A commit still becomes visible and answered only once its decision is written. Other durability levels are unchanged.
- The bench's warmup now waits for the store's first pack from all shards (D242's third amendment), so a run that packs measures its packed placement, not its 16-19 tablet moves. The JSON records `detail.warmup_settle_secs`, the seconds into the warmup at which the placement settled. The warmup's cap is now 60 s with or without a durability switch (it was 30 s without one). This changes the gate's methodology: a warmup can now run up to its cap where it used to end after the 2 s quiet window.
- A filtered scan or row read (a qualifier prefix or range, or a time range) no longer walks a memtable's later rows when that memtable has nothing it admits near the read's position. Previously, such a memtable stepped through every later row of the tablet, looking for its next admitted entry, while other sources supplied the rows the read returned. Results are unchanged. Filtered scans over a memtable that holds mostly newer data get much cheaper: on the benchmark's time-series-range workload, each scan stepped through 23K entries against RocksDB's 6.9K. SST sources follow in a later release (D288).
- Reads of hot counters no longer slow down with the number of increments since the last flush (#713, D291). A counter read that folds many increments now leaves its result in memory, so the next reads of that counter fold only what came after it. Read results are unchanged at every snapshot. In the counters benchmark, the counter-read p99 fell from milliseconds to tens of microseconds.
- **The shard-thread load controller is on by default, and `Options::adaptive_shard_threads` is public again** (D289, #1015, ICR 0081/0085 amended). An engine-owned database starts a thread per shard and moves a light load's shards onto fewer threads, which sleep less, so commits wait less for a wake; under load it spreads them out again. In the 2026-10-28 gate, sparse-wide's `Buffered` put p99 fell from 545–909 µs to 66–107 µs with throughput level, and transfer, ycsb-a and ycsb-f were level. `adaptive_shard_threads(false)` keeps the earlier behaviour, a thread per shard; a set `shard_threads` also turns the controller off. `phdb-bench` gains `--no-adaptive-shard-threads` for A/B runs.
- The shard-thread load controller (`Options::adaptive_shard_threads`) resizes the shard threads steadily (#1015). It adds threads when shards wait on each other's turns, or when a thread is almost always busy. It removes them only when the work is light and threads keep parking, and it never goes below two. It no longer adds threads for long background turns alone, or undoes a shrink on a short dip in throughput. On the reference machine, a wide-row write load with it on now keeps put p99 at 67–142 µs, against 391–623 µs with one thread per shard, while transfer, ycsb-a and ycsb-f stay level.
- On Linux, async reads served from the OS page cache are faster (#749, D292). A block read that the page cache already holds is now copied on the thread that asked for it, rather than waiting its turn on the io_uring ring or the read pool; reads it doesn't hold are submitted as before. Results are unchanged. In the benchmark's async ycsb-a, with 16 operations in flight per client, throughput rose by about a third and the read p99 fell from about 1.2 ms to 350 µs.
- Scans: a scan whose row limit leaves at most 128 rows to return now starts reading blocks ahead only after 8 blocks, instead of 2 (#1029, #712). Short scans finished before their readahead arrived and then waited for it, which made up most of ycsb-e's p99. A short scan that turns out long in blocks still reads ahead (a wide row, rows a filter skips, a run of deleted rows). Scans with no limit, or a larger one, read ahead as before.
- Docs: getting started's tuning bullets start from `cpu_profile`, with `shards`, `shard_threads` and `compaction_cores` as overrides. Getting started and the agent reference also give the memory a writer can use at the defaults: up to about 0.6 GiB at 4 physical cores, 1.3 GiB at 16 and 4.3 GiB at 64, filled only under load. A single memory budget is planned after 1.0 (#1041).

### Fixed
- **A close no longer hangs when a voided purge guard refuses the flush of its in-place memtables** (#838). A close whose arena had no chunk left flushes its active memtables in place (#111); when that flush also carried a frozen memtable whose purge guard a delete had voided (#287), the manifest refused the whole flush and only the frozen memtables were queued again, so the in-place ones were never flushed, their log records stayed needed, and `close()` waited for ever (the shard idle, nothing to flush). The refused flush now re-queues them too, and an I/O error on such a flush counts as a failure (the close gives up, unclean) instead of a retry. Present since 0.2.0 (#315). Found by the public model check's recovery arm (#837).
- **The close waits for the WAL's submitted I/O** (#824). A spare segment's zero-fill and a held successor header are submitted to the I/O backend and were never waited for, and a failed shard's close waited for nothing, so a close followed by a reopen in the same process (the recovery guide's procedure) could hand the file over with such a write still in flight on the pread backend's threads, and the reopened instance could start a segment in the slot it then landed on. The close now returns, and releases the writer lock, only once every stream's submitted operations finished, so no opener, in this process or another, can reuse a segment slot under a late write; a second `close` made meanwhile waits for the whole close too. On a device that never answers the close blocks, as a sync would, and so does dropping the last `Engine` handle.
- An older build no longer silently misreads a file a newer build wrote (#496):
  - **A newer superblock slot** (valid checksum, newer version) is never passed over for the other slot. The open refuses with `UnsupportedFormat` rather than opening an older root the newer build may have freed.
  - **A newer WAL segment** (valid checksum, newer version) refuses the open. It used to be read as a blank or torn slot, and with every segment newer the stream read as empty, so its commits were silently missing.
  - **A WAL fragment of an unknown type** whose CRC passes is `UnsupportedFeature`, not a torn tail.
  - **A refused open never upgrades the file:** an open refused for an unregistered merge operator now refuses before upgrading the file's superblocks, leaving an older file as it was.
- docs.rs now documents `pigeonhole-arrow`'s `ffi` feature (`ArrowScan::into_ffi_stream`), which it left out because it builds default features only.
- A reader process pins only what its live snapshots need (#693, #39). An idle reader, with no snapshot alive, used to keep its last snapshot's memtables and file space pinned until it took another snapshot, and a reader whose snapshots overlapped never let go of its oldest. A long-lived, mostly idle reader could fill the writer's memtable budget and make its commits fail with `Busy`. Now the pin is always the oldest live snapshot's, it moves up as snapshots are dropped, and a reader with none pins nothing.
- Two processes closing a database at the same moment no longer both decide another is still open and leave the shared memory behind (#150): one that can't upgrade its presence lock releases it and retries.
- Write stalls at high concurrency: a shard reserved three memtable chunks of arena room for every commit waiting in its group, whatever its size, so about 85 small commits pending on one shard filled the reservation with the arena nearly empty. The rest then waited for room that flushes of near-empty memtables "freed": thousands of tiny flushes, a deep L0, and throughput down to a tenth with 20 ms p99s (#749). A group's commits now reserve each memtable's chunks once between them.
- A cross-shard transaction or `commit_if` refused because it overlapped an older cross-shard commit's undecided share waits for that older commit to move on (D249). If the older commit was retried after a tablet split, merge or move and all its rows now lived on one shard, it never said so, and the younger commit waited until the write-stall timeout and failed with `Busy` (for ever with a stopped clock). It is now released as soon as the older commit leaves two-phase commit. Nothing was lost or reordered: the commit was only delayed, then refused (#772).
- A cross-shard commit refused behind an older one (D249) waited for ever if the older commit's retry was answered with an error at its own coordinator, whose WAL had failed or which was closing, before any further attempt: the retry now releases the commits waiting behind it. In 0.3.x this hit cross-shard transactions and `commit_if` after an I/O error (#776).
- A flush on a store running many cross-shard commits no longer scans every unreported share on its shard thread to find the flushed ones (17-21 ms with ~100K): the shares are indexed by the slots they write, so a report touches only the shares it reports (#777).
- A compaction triggered by a flush no longer keeps every version that flush wrote. It used to count the flushed memtable as a source above its inputs until the shard finished handling the flush, so a family with `max_versions`, or rows with deletes, kept the extra versions and markers until a later compaction rewrote them (#805).
- `compact()` now drops what it promises (versions beyond `max_versions`, expired cells, tombstones no snapshot needs) from a slot left with a single SST too. It used to move such an SST to the last level unchanged when tablet changes were off, and leave one already there unchanged whether they were on or off; one written while a snapshot or the flush of a memtable held its purge back kept every version and marker it held. A lone SST whose metadata shows delete markers, cells past the family's TTL, or more entries than rows in a family that keeps `max_versions` is rewritten instead, once per `compact()` call (#805). A table with several columns per row in a `max_versions` family always looks like that, so each `compact()` rewrites its lone SSTs once.
- `compact()` now purges a last level of several SSTs too, when one of them may hold purgeable entries: versions beyond `max_versions`, expired cells, tombstones no snapshot needs. A run written while a snapshot held its purge back used to keep every version and marker through every later `compact()` (#820). An SST written by a compaction that nothing held back now records that in its properties (D268), so a table with several columns per row in a `max_versions` family is not rewritten again by each `compact()` call; SSTs written before this change are rewritten once.
- A `RowIter` or `RowStream` held past `Pigeonhole::close` now fails with `Closed` on its next step and then ends, as every other handle does (#826). It used to keep reading the closed engine's view, so once a new writer on the same file reused those pages, it read about a thousand more cells and then reported corruption. Owned scans (`Scan::into_owned`) and the Arrow C stream make holding an iterator past `close` common.
- The writer now frees the slot of a reader process that has exited or was killed (#833). A crashed reader's pin used to hold the writer's retired memtables, view versions and extents until the next writer started, so a long-running writer could end up failing commits with `Busy`. The writer checks reader liveness at most every 250 ms, before each reclamation. A live reader's slot is never freed, provided readers share the writer's PID namespace (the existing requirement). On Linux, a reader that `/proc` hides (under `hidepid`, another user's process) now counts as alive. A reader wrongly judged dead gets `SnapshotExpired` and a fresh slot at its next snapshot, never wrong data or another reader's slot. That includes a reader in another PID namespace, which isn't supported: it now sees `SnapshotExpired` repeatedly, because the writer keeps judging it dead.
- On a stopped clock (the simulator's, or a test's), a `flush` or `compact` waiting for arena room that in-process snapshots hold no longer gets `Busy` while a cross-shard commit's share is still undecided on that shard, or a group's sync is in flight there (#839). It waits for them, as a write waiting for room already did, since the decision may free room. On a running clock nothing changes: the callers wait up to `write_stall_timeout` as before.
- **A flush on a shard whose WAL stream failed can no longer make a commit durable in part** (#847). A flush's sync barrier on a poisoned stream (a write or sync had failed) answered that the stream held once its cross-shard records were durable, which a single-shard database meets at once; so a flush in flight at the failure committed its SST and `SetFlushed` over records the log never held. A `None`-durability commit is applied before its buffered record reaches the file (it goes with the next group's write, the one that failed), so its cells in the slots that flushed survived the reopen and the others did not: the public model check's recovery arm read a part of such a commit after a recovery. The shard's own barrier now holds on a poisoned stream only if the stream is durable through everything appended; a peer's barrier keeps the cross-shard rule (D115, amended). The flush fails instead, the close gives up and is unclean, and the next open replays the log: the commit is there whole or not at all. Present since 0.2.0 (#159's barrier rule for a failed stream; a `None` record is buffered until the next group's write).
- A database handle used in a process forked from the one that opened it no longer runs the parent's engine (#901). Before, closing or dropping the child's copy ran a full close on the parent's database (flushes, log writes, a root commit) and could hang on threads that exist only in the parent; any other operation could hang or read shared memory the parent was reusing. Now every operation on it fails with `Unsupported` ("opened in another process (fork); open it again here") at once, and close and drop do nothing (ICR 0067). Open the database again in the child. Only `fork(3)` is detected (`_Fork`, `vfork` and a raw `clone` skip fork handlers).
- The tablet balancer's commits-in-flight measure (D257) counts a commit only for its part inside the interval it ends in. A commit whose sync outlasted several balancer intervals used to count all of its time in the last one, so one blocking client could read as several commits in flight and skew the shard-packing decision (#922).
- `pigeonhole`: with `Options::auto_recover` on, a commit that met a failed shard just before the recovery began closing it now gets `Busy` (a plain commit) or `SnapshotExpired` (a transaction, which `transact` retries) once the database has recovered, as a commit refused during the recovery already did; it used to get `Io` (#925, #921). Without `auto_recover` it is still `Io`.
- `pigeonhole-io`, `pigeonhole`: in application-owned mode on io_uring, a shard thread whose own ring the kernel refused (`ENOMEM` against the locked-memory limit, or a kernel without the needed support) could leave its WAL syncs unreaped on the shared ring, hanging flushes and commits. Such a thread now runs its I/O inline, as the pread backend does, and retries for a ring later (#938, #929).
- With `Options::auto_recover`, a commit the failed engine refused before logging it could fail with `Io` (#966): after the supervisor gave up (`recovery_stats().gave_up`), when it reached the failed shard just before the database was marked dead; and for async commits and commit tickets, which do not wait, during a recovery too. A sync commit, an async one and a ticket, whether the failed shard refused it or the failed engine's close did, now all get what the recovery guide says: `Busy` once the recovered engine is in (`SnapshotExpired` for a transaction), `Closed` while the recovery runs or after a give-up. None of them was committed.
- io_uring backend (#976): when the kernel refused for now the system call that hands queued requests to it (`EAGAIN` under memory pressure), the backend failed requests the kernel could still run, and freed or reused their buffers:
  - a read or write whose own submission was refused failed at once, though it stayed queued and the next call handed it over;
  - a refusal of the completion thread's call (or of a thread reaping its own queue) failed every request in flight, and the shared queue's completion thread then stopped, so later requests never completed.

  The kernel could then read into, or write from, memory the request no longer owned. A refused call is now retried, and nothing queued or in flight fails because of it. If a queue breaks for good, its requests fail but their buffers are never freed.

- **A close frees a running compaction's output** (#991). A compaction still writing when `close()` began kept running, and the close could end without it, so its output stayed allocated in the file until the next open reclaimed it. A running compaction now stops at its next slice once the close begins and frees what it wrote, and the close ends only after that, so the file holds no dead extents after `close()`. A compaction that has already submitted its result is not stopped: the close waits for its commit, as before.
- io_uring: a thread blocked on an operation in flight on another thread's ring now keeps completing its own ring's operations while it waits (#1002). Before, it only slept, so two threads each waiting on I/O in the other's ring could hang for good. No path that does this is known in 0.3.x, but D289's shared shard drivers would have made it routine.
- **A background worker's blocked tasks are no longer taken back as if it had stopped** (#1012, D284). After 100 ms without a pass, the shards took back everything a worker held, including tasks waiting for a wake rather than for the worker. A worker inside one slow slice (an inline sync on a slow device) lost them although it was being driven: a flush moved back to its shard, and a compaction was dropped and redone. Now only tasks that could run are taken back (runnable, woken, failed, or asleep past their deadline), and none while the worker is in the middle of a slice.
- A malformed data block whose entry claims a huge shared-key length now fails with a corruption error during a filtered scan's column skip. Previously, a debug build panicked on the overflow, and a release build could skip the malformed entries without reporting them. Only a deliberately crafted block with a valid checksum could reach this; random damage fails the checksum first. Found by fuzzing (#1035).
- `phdb load` refuses an input without a `phdb dump` header, an empty one included, before it opens the database (#1037). A `phdb dump` that failed into a pipe writes nothing to standard output, and `phdb load --create` used to load that as an empty database with status 0. Now it fails with `BadInput` and status 2, and `--create` creates nothing. A first line that isn't the header, which already failed with status 1, now also fails with status 2. Blank lines before the header are skipped. To create an empty database, load a dump with only its header: `echo '{"phdb":1,"command":"dump"}' | phdb load --create app.phdb -`.
- **A compaction's output is freed once, not twice, when its table is dropped just before the compaction commits** (#1056). If a `drop_table` committed after a compaction had checked its table but before the compaction's own manifest commit, the manifest freed the compaction's output SST twice: once as an orphan, and again as the refused request's output, for a compaction with a purge guard or new blob files. Another flush or compaction allocating space between the two could lose an extent it still used, which it then published over free space. Present since 0.2.0.
- `phdb check` (and `pigeonhole::check`) now reports two structures that the manifest places on exactly the same extent as an allocation overlap. Previously, only partial overlaps were reported, so a double allocation went unreported unless one of the structures also failed to parse.
- `phdb check` now refuses a file that uses an incompatible feature it doesn't know, in either superblock slot or in a WAL segment header, as it refuses a newer format version. Previously, it reported the superblock case as corruption (exit 3), and it treated such a WAL segment as a blank slot, so the segments after it were reported as unreachable (#1060).
- **Application-owned mode with background workers: an engine dropped without `close()` after its shards no longer leaks** (#1070, D284). A flush or compaction a worker held or had queued was handed back to its shard's queue after the shard was gone, and kept the engine's state, its files and the shard's queue alive in a cycle. Tasks handed back to a dropped shard are now dropped. No release contains D284.
- `Pigeonhole::shrink` no longer grows the file while a snapshot or backup is held. Before, with a snapshot pinning space a compaction had freed, each shrink round moved the manifest past the end of the file and planned to move it again, so a call could add megabytes (1 MiB grew to 3.5 MiB in the report, #1098). A shrink now moves the manifest only into free space below it while anything pinned would keep the old copy, and gives back less in that case; a shrink after the snapshot is dropped gives back the rest.
- Reader processes: opening a database whose file reuses a deleted database's inode now fails with `ErrorCode::NoWriter`, not `ErrorCode::Corruption`, until that database's writer runs (#1133). Shared memory is named by the data file's device and inode, so a writer killed before deleting its database left a region the new file found. The new database's writer now removes that region and starts its own at generation 1. A reader never mapped the old database's data: its database id check refused it.

## [0.3.0] - 2026-10-20
The **Phase 3 latency engine**: io_uring and direct I/O, an async form of every data operation, commits visible once applied with group syncs shared between them, one-I/O cold gets, thread-per-core shards that are pinned and packed by load, cross-shard commits that stay ordered and cheap under contention, and the work measured against the Phase 3 gate on the reference machine (2026-10-20 at 516b59b8; see [Performance](#performance), and [Known issues](#known-issues) for what carries over to Phase 4). Several defaults and error semantics change; read [Upgrading from 0.2.x](#upgrading-from-02x) first. The file format is unchanged, and files written by 0.2.x open as before; the shared-memory layout moves to version 2, so stop reader processes before upgrading the writer. Includes the fixes released in 0.2.1, 0.2.2 and 0.2.3. Every published crate moves to 0.3.0 together.

### Latency engine: commits
- **Commits are visible once applied, not once durable** (D227 part 1, amends D19). A shard publishes a group's seqnos once its WAL records are handed to the OS and the group is applied, without waiting for its fsync. A commit's own call still returns only once it is durable at its level and visible, and cross-shard commits are unchanged. Readers, reader processes and backups can therefore see `GroupSync` and `Sync` commits that a power loss then removes; across shards, a later commit can survive an earlier one it was derived from, and a seqno or default timestamp a reader saw can be handed out again after a power loss. The durability guide's "Visibility and durability" section has examples.
- **Durable snapshots** (D227 part 2, ICR 0037): `durable_snapshot()` on the writer and on reader-process handles sees a commit only once it is durable at its level (the view every snapshot had before), and `backup_durable` takes a backup from one. A memtable freezes only once everything in it is durable, so a flush never collapses a version a durable snapshot reads; a freeze may wait for the fsyncs in flight.
- **Durable group commits share their syncs** (D207, #412). A shard keeps a bounded number of group syncs in flight per WAL stream (2 on Linux, 1 on macOS; D221), and commits that need one meanwhile batch behind them and share the next. At 16 clients: Linux 29.5K → about 31.5K ops/s with p99 1.46 → about 1.0 ms; macOS 578 → 2.2K ops/s with p99 33 → 11.6 ms.
- **A commit writes no engine-wide memory on its way** (D236, amends D210): an async commit is charged on the admission count of the shard it is routed to, and a pending commit holds its shard's handle instead of a reference on the engine's shared state. 16 pinned shards commit 11.6% faster on the reference machine.
- **In application-owned mode, `Shard::run_once` returns early when it completed a future woken through `Shard::waker()`** (D237). It returns `true` right after the shard's queued work, before its background work (flush, compaction), so the loop polls the commit sooner; background work runs on the next call, and at the latest on every ninth. On the reference machine's 16-shard durable group commit this lowers the p99 by about 20 µs at 16 commits in flight and about 30 µs at 8. See [Upgrading](#upgrading-from-02x) for the loop change it needs.
- **Async commits wait for room before they submit** (D210, #149). Each shard holds at most half `memtable_budget` of async commits submitted and not yet resolved (32 MiB at the defaults); over that, async commits wait in arrival order. A commit future dropped while it still waits writes nothing; blocking commits and `commit_with_ticket` are neither counted nor held. An async commit that waits for room is one state of the engine's pending commit, about 43 instructions less per uncontended `commit_async` (ICR 0036).
- **Nothing slow on the commit path:**
  - A WAL segment rollover no longer waits on the shard thread for the full segment's sync: only the successor's header waits, and its records are written meanwhile (D200, #19; FORMAT §10.1 rule 1). A rollover with no spare slot ready holds the group back instead of growing the stream file inline. `WalCounters::rollover_blocks`/`rollover_waits` and `Metrics::wal_rollover_blocks` count it.
  - WAL spare slots are prepared in short submitted steps (D35), not a ~30 ms zero-fill and sync on the shard thread.
  - The page file grows ahead of need, off the allocator lock (D58, #182), and a submitted root commit no longer waits on the I/O backend for a growth's or truncation's sync. `PagerStats::growths_ahead`/`ahead_nanos` and `Metrics::file_growths_ahead` count it.
  - WAL pin passes (D155) run from an index of the log in slices averaging under 50 µs, instead of scanning the shard's whole log for 6–11 ms (D206, #474).
- **Opening after a clean close waits for no flush** (D203, #158): open to first read on macOS goes from about 17 ms to about 1 ms. A `GroupSync` or `Sync` commit right after the open waits for the new WAL files' syncs instead.
- **Fewer allocations and copies per commit** (#320):
  - the batch buffer is handed back and reused, and completion slots are recycled per thread: allocations per one-cell commit go from 5.25 to 2.25 (#458, #498);
  - the WAL frames records straight from the batch, so a value committed on one shard is copied three times instead of four (#608);
  - a separated large put and a view publish after a manifest commit reuse what didn't change: 92 allocations per 1 MiB put instead of 113, and 80% fewer on a one-cell flush against 2,048 SSTs (#499).
- **Cheaper visibility waits:** waiters register in one part per shard, keyed by waiter (#154); a publish visits only the shards that list a waiter, one load when nobody waits (#580); a publish below every waiter's seqno skips the list without its lock (#134); a commit wakes a thread waiting in `Shard::wait` directly (#577).
- Fixed: a conditional commit (`commit_if`, `check_and_mutate`) waited for the next group commit, and paid an extra sync at `GroupSync`, whenever an earlier commit in its group wrote any cell of its row. It now waits only when that commit wrote the cell its condition reads (or deleted its family or row), and only later commits on its rows wait with it (D260). Contended read-modify-write workloads had paid an extra sync on a few percent of commits.
- Writes escape their row keys with a word-at-a-time search for zero bytes (#406).
- New counters: `Metrics::visibility_waits`, `visibility_wakes` and `visibility_contended` (ICR 0023), `Metrics::shard_idle` and `commit_parks` (ICR 0027).

### Cross-shard commits
- **Fixed: a cross-shard commit could get an earlier default timestamp than a later write on one of its shards** (D244, #653; also in 0.2.3), so a later write could be hidden by an earlier one on the same cell (D11). A single commit queued on a shard behind a cross-shard commit's PREPARE could land below it, and with tablet changes off a share could land below its shard's earlier writes. Admitted PREPAREs now raise the shard's timestamp floor before the group's singles are stamped, and a PREPARE out of seqno order with a write its shard already stamped is refused and retried, with tablet changes on or off.
- **Contended cross-shard commits are refused far less** (D245, #637). A participant compared a PREPARE's timestamp against everything it had stamped since, in any order; on a 16-shard contended load the default configuration ran about 36 times slower than with tablet changes off. The check is now exact by seqno, and the coordinator raises each participant's timestamp floor before it reserves the commit's seqno, so the participant's later writes always land above the commit.
- Fixed: a cross-shard commit whose share waited for memtable room on a participant could hold back the durable watermark that the participant's freeze needed, so room never freed (#655). The share is now refused and retried once the participant has freed room (D245). 0.2.3 does not have this fix.
- **A cross-shard transaction no longer fails with `Conflict` just because another cross-shard commit had a share on the same rows still undecided** (D249). Its PREPARE is refused and retried, with the same snapshot and reads, once that share is decided; a commit that only overlaps an earlier commit in the same group waits for the next group. `Conflict` now means a real conflict: a write to a row the transaction read, after its snapshot. Two cross-shard commits that each meet the other's undecided share resolve in submission order. A retry that cannot get through before `Options::write_stall_timeout` fails with `Busy`.
- **A flush that puts many cross-shard commits in SSTs sends one message per shard, not one per commit** (D254, #716). The flush's own turn on the reference machine went from 42–67 ms at most to 21–29 ms, with about 10× fewer long shard turns. The WAL checkpoint and the share scan around a flush are bounded too (below).
- **Fixed: a shard popped every record its WAL checkpoint could pass in one handler run** (#764, #727, #763). After a flush report, a settle or a flush install that freed thousands of records, that held a turn for 3–5 ms, and the shard's pending watermark with it; on the reference machine's cross-shard row it happened about five times per shard per second and caused the row's 0.4–0.5 ms p99.9 with packing off. A batch now pops at most 64 records, and the rest follow on the next batches with one checkpoint edit for the whole run; a closing shard still drains its log in one go. An aborted cross-shard share runs a checkpoint pass only when its record is the oldest in the log.
- **Fixed: a shard rescanned every applied-but-unflushed cross-shard share on every manifest commit anywhere in the store** (#761): an SST, a WAL checkpoint, a flushed seqno or a tablet change each cost 1–3 ms inside a turn, which held the visible watermark for every client. After a packed load regrew, that was 20–60 scans a second per shard on the gate's cross-shard row. The scan now runs only when one of its shares' slots flushed further: on the reference machine +4–6% ops/s, and the packing-on p99.9 halved (3.0 → 1.7 ms after a regrow, 1.1 → 0.6 ms at 16 clients).
- Fixed: application-owned stores with cross-shard batches no longer stall commits into `Busy` under a storm of refused two-phase rounds; recording each aborted round scanned the shard's whole log of recent commits and is now a lookup (#688).
- `EngineMetrics::cross_shard` (`CrossShardMetrics`, ICR 0043, ICR 0045): two-phase rounds, the rounds a participant refused (wasted rounds per cross-shard commit), and the refusals by reason (timestamp below the participant's floor, below a moved tablet's floor, a tablet change, no arena room, an undecided overlapping share).

### Async front door (#42)
- **The `async` feature is on by default** (D17). Every data operation has an async form: `get_async`, `get_at_async`, `RowRead::read_async`, `Scan::stream`, `commit_async`, `commit_with_async`, `commit_if_async`, `Transaction::get_async`, `commit_async` and `commit_with_async`, and `Pigeonhole::flush_async` and `compact_async` (D196, ICR 0018). They run on any executor (no runtime dependency, no `spawn_blocking`) and on an application-owned shard's own event loop. `backup`, `shrink`, open, close and the schema calls stay blocking. Build with `default-features = false` to drop them and their `futures-core` dependency; the blocking API is unchanged.
- **Async reads** resolve to owned values. Memtable and cache hits resolve on the first poll; a block the cache lacks is read through the VFS's asynchronous reads. `Scan::stream` fetches each step's blocks one block ahead, as it is polled. `Pigeonhole::async_sync_reads` counts the reads that still go to the file synchronously.
- **Commit futures** submit at the call and resolve when the commit is durable at its level and visible. Dropping one after it submitted does not roll the commit back. `WriteBatch::commit_with_ticket` returns a `CommitTicket` (D196): `wait`, a non-blocking `try_result`, `seqno` once resolved, and `.await` with the feature.
- A user-guide page on the async front door (`docs/guide/async.md`): the call table, executors, cancellation, the counted synchronous fallbacks and the sync-only calls.

### I/O backends and application-owned mode
- **io_uring** (#402): `Options::io_backend` and `ReaderOptions::io_backend` choose `IoBackend::Pread`, `IoBackend::Uring` (Linux; the open fails with `Unsupported` where it is unavailable) or `IoBackend::Auto`, the new default (see [Defaults](#defaults)). Each shard thread gets a ring of its own and completes its I/O in its turns and waits. Rings register a pool of buffer slots with the kernel, up to half `RLIMIT_MEMLOCK` (`Pigeonhole::io_rings` reports how many got one). A quiet turn makes no system call, and a wake writes the ring's eventfd only while its thread waits in the ring; those cost write-heavy workloads 15–20% against pread before.
- **Direct I/O** (#403): `Options::direct_io` and `ReaderOptions::direct_io` (default off) read and write SST and blob extents through a second handle opened for direct I/O, so the block cache is their only cache. Superblocks, the manifest and the WAL stay buffered, and a file system that refuses direct I/O keeps buffered I/O. Size `block_cache` for the working set with it on.
- **Application-owned mode starts no engine threads with io_uring** (D202, #408): the threads that drive shards reap the shared ring. `Shard::io_fd` turns readable when the driving thread's I/O has finished, for an application's own `poll`/`epoll`.
- **`Shard::wait(timeout)` and `Shard::waker()`** (ICR 0035): `wait` blocks the driving thread until the shard has work again (a commit or message, a `waker()` wake, the thread's own I/O, due background work, or the timeout), on every backend with no file descriptor. Give the futures the driving thread polls `shard.waker()`.
- **`Shard::release()`** (ICR 0029): call it before handing an application-owned shard to another thread. With io_uring only the submitting thread can complete its I/O, so `release()` drains it first; debug builds panic on a move that skipped it.
- `Table::shard_of(row)` (ICR 0022): the shard that owns a row now, a routing hint so an application-owned shard thread can commit the rows it owns with no handoff. Commits stay correct whatever it says.
- Fixed: a thread blocked on the WAL or on the manifest writer behind I/O on a ring no thread reaps now reaps it (ICR 0028, #306, #473); a shard moved to another thread gets a ring on that thread; `Shard::wait` no longer sleeps through a `waker()` wake that arrived during `run_once` (#592).

### Reads
- **A cold point get is one I/O** (#406): the gate measured 1.106 device reads per get before.
  - A point get or single-row read whose row ends a data block no longer reads the next block to learn that the row ended (ICR 0039, #611). SSTs mark where a row ends in their index when neighbouring rows differ by one byte; existing SSTs read as before and gain once compacted.
  - `engine_metrics()` reports the SST top indexes and filters pinned in the block cache: `block_cache_pinned_bytes`, `block_cache_capacity_bytes` and `block_cache_pinned_warnings` (D215, ICR 0032). Past half the cache, index partitions no longer stay cached and a cold get costs two reads: size `block_cache` to at least twice `block_cache_pinned_bytes`.
- **Reads skip superseded versions** (#387). A process-local stale-tail index beside each memtable lets row reads and scans pass a column's older memtable versions in one jump (D194, D199, ICR 0013; ycsb-c −43% instructions on Linux callgrind; an overwrite costs about 200 more to record), and SST sources pass a finished column's entries reading only their block headers (ICR 0041; scans 1.7–2.4% fewer instructions). Results are identical.
- **The row cache works** (D201, ICR 0019): `Options::row_cache(bytes)` used to do nothing. It serves latest row reads of the newest version and point gets from cached family rows; a write or a TTL expiry makes the cached copy miss at once. `Options::row_cache_max_row` (default 4 KiB), `Options::row_cache_family` and `Pigeonhole::row_cache_stats`. It is on by default now (see [Defaults](#defaults)); snapshot reads, multi-version and time-range reads, scans and reader processes don't use it.
- **Point reads** find a row's SSTs by a binary search over each level below 0 (ycsb-c −8.5% instructions; no slowdown as SST counts grow), and skip a skiplist search in memtables that hold no delete markers (ICR 0020; get-mem −16%).
- **Scans:**
  - readahead submits fetches for the next 16 blocks the cache lacks, unmerged (D222, #402): 3.2–3.6 GiB/s on cold tables on the reference machine, against 2.6 GiB/s with none;
  - filtered scans compile their filter once (ICR 0030), seek forward within a block, and walk the index forward to the target block (#29);
  - a scan sets up nothing for families with no data in a tablet's range, and stops at its row limit without reading the next row (a 10-row scan with 3 of 4 families empty: 9%, then another 10%, fewer instructions);
  - each cell is read once to append it to its row (#607), and row keys are unescaped in one copy (−13% on a time-series newest-ten scan);
  - compaction and uncached scans reuse decompression buffers per SST (#372).
- **Block-cache hits scale across threads** (#18): 10 threads hitting the cache, 371 → 106 ns per hit; ycsb-c with 8 client threads on one shard, 863K → 1.67M ops/s.
- Fixed: the block cache's hit and miss counts read 0; they are now counted (`EngineMetrics::block_cache_hits`, `block_cache_misses`; #57).

### Tablets and balancer
- **Tablet packing** (D217, ICR 0034): the balancer packs a lightly loaded store's written tablets onto as few shards as their summed busy time needs at half load each, and spreads them again as load grows. `Options::tablet_packing(false)` keeps the 0.2 placement exactly. `shard_stats()` reports each shard's `busy_nanos` and `engine_metrics()` their sum (ICR 0033).
- **Packing sizes the active shards by the commits in flight** (D257): about one active shard per 0.75 client commits outstanding, so one client's load packs onto a few shards while concurrent clients keep what they can use. On the reference machine ycsb-a at one client went from 14 to 3–4 shards (+25%), time-series-ttl from 16 to 2 (+31%), and sixteen buffered clients settle on nine (+9%, write p99.9 105 → 43 µs). `Metrics::shard_commit_inflight_nanos` and `ShardStats::commit_inflight_nanos` report the measure.
- **A cross-shard commit's time in flight counts at every shard its round occupies** (D262, amends D257): a client with a two-shard commit outstanding counts as two shards' worth, so sixteen clients committing across shards keep sixteen active shards instead of shrinking to 13–15 and moving tablets under the load. `shard_commit_inflight_nanos` and the per-shard stat rise accordingly.
- **Packing counts the load it can't see in thread time:** a shard is busy while its group fsyncs are in flight (D248, `ShardStats::sync_busy_nanos`), while its commits wait for memtable room or are paced on L0 depth (D255), and while the compaction pool works on its flushes and compactions (D256, `ShardStats::pool_busy_nanos`, `spin_time_nanos`). It adds active shards when any active shard's thread stays above 90% busy (D251), and a growth from a stalling or saturated shard holds while the load does. Application-owned stores stay unpacked.
- Fixed: with flush and compaction on their own threads (D252), a shard under a full write load read as idle, so packing gathered whole tables onto one or two shards and moved them back out as those saturated. On a 16 GiB random load one shard held 86 tablets, flushed sub-megabyte memtables by the thousand and wrote 45× its data; buffered ycsb-a at 16 clients packed onto 4–5 shards at 812K ops/s and now runs at 1,122K (D255, D256, #734). The first shrink from the unpacked start now waits for a full 30 s window of writes, so a load's phases no longer pack the store between them.
- Fixed: write skew now moves small tablets off a shard that holds many equally loaded ones; it moved only a dominant tablet, so one shard could stay saturated beside idle ones (D251). On the reference machine, cross-shard contention with tablet changes on had run at about half the speed of tablet changes off.
- Fixed: under packing, every shard uses the same count of active shards, decided by shard 0. Before, shards could disagree for good and place tablets on fewer or more shards than the load called for (#641).
- **Damped, closed-loop placement** (D214, D224): the balancer moves or splits for write skew only after it has lasted 10 passes (1 s), then sheds load until the shard is within 1.1× the mean, with as many pieces as the skew needs. Skew that appears only because other shards went idle no longer moves tablets; placement is corrected on loads averaged over about 10 s, one change per 10 s; shards balancing at once never shed into the same shard; a tablet must go unwritten for 100 passes (10 s) before it is merged or consolidated. Reacting to a real, sustained skew takes about 1–3 s longer.
- **Fixed: a table loaded faster than it compacts now splits and spreads over shards** (D241, #636). The balancer skipped the split whenever the tablet was compacting, which under a bulk load was always, so the whole load stayed on one shard. A split due on a compacting tablet now starts when the compaction ends.
- Placement is judged on its own (D231): `phdb-bench placement` offers skewed writes open-loop and passes when the table settles within 60 s, nothing changes while measuring, and the busiest shard takes at most 1.25/N of the writes (D223). The scaling gate pre-splits with the balancer off and judges efficiency alone.

### Stalls and errors
- **The L0 write stall starts at twice the compaction trigger** (8 L0 files at the defaults) instead of the trigger itself (D234): writers are no longer paced while a compaction is merely running. A single shard wrote ~6% more on the reference machine.
- **The write-stall timeout is each waiting write's own** (D240, #638): `Options::write_stall_timeout` counts from when that write, `flush` or `compact` began waiting. Before, a shard short of room for the whole timeout refused every waiting write with `Busy` at once, including ones that had just arrived.
- **Cross-shard commits that keep meeting tablet changes or a participant's timestamp floor fail with `Busy` only after the write-stall timeout** (D241, #636), not after 16 refusals within seconds. The `Busy` message names tablet changes as a cause and refers to `Options::write_stall_timeout`.
- **A write waiting for room with no flush in flight freezes the largest memtables, about half the arena,** instead of every open one (D124, #642). A shard holding many tablets flushes fewer, larger SSTs and stalls less: locally, a 16-tablet hot shard went from 109–245 background jobs and 1.2–2.9 s of stalls to 31–44 jobs and about 0.1 s.
- A write stall admits commits at its designed rate where the timer is coarse (#149): a single committer on Windows was throttled about 5× harder than designed.
- **`ErrorCode::OutcomeUnknown` (28) and `Error::OutcomeUnknown`** (ICR 0038, ICR 0040): a commit whose outcome is not known in this process, because a shard failed or the database closed after its records may have reached the log. Reopen and read: the next open decides it, all of it or none of it. **`Closed` now always means the commit was not committed.** A visibility wait that ends because the database closed or a shard died, a commit whose apply or WAL sync failed after its write, and one in flight when a shard panicked now return `OutcomeUnknown` (they returned `Closed`, `Busy` or `Io`). `Io` for a commit means it was refused before anything was written.
- **A health check** (ICR 0040): `Pigeonhole::is_failed()` (one atomic load) and `failure()`: which shard failed (`Failure::MAIN_FILE` for a failed manifest commit) and why (`FailureCause::{Panic, DriverDropped, Io, Internal}`). The user guide's new "Recovering from a failed shard" page says what to do next. A shard poisoned during a tablet change now records its failure (#634).
- **A shard's death stops every commit** (D85 since D227): after a panic, a dropped application-owned shard, a failed WAL fsync or a failed cross-shard apply, every new commit fails at once with `Closed`, on healthy shards too. Reads keep working; the close is unclean, and the database needs reopening. A failed fsync's commits never become durable, so durable snapshots and `backup_durable` never include them.
- **Close hangs fixed:**
  - a shard dying in the middle of a cross-shard commit: the commit is aborted (`Closed`) if undecided, fails with `OutcomeUnknown` if decided, and is never partly visible;
  - a shard stopped after a failed apply: the close gives up flushing it, reports unclean, and the next open replays its log;
  - a flush failed after a WAL write error: the close no longer restarts it indefinitely, rewriting the same SST and growing the file; a `flush` or `compact` racing such a close gets `Closed` at once.
- Fixed: after a power loss shortly after a database was created, or after its shard count was raised, a later crash could lose acknowledged commits (D211, #520). A WAL checkpoint now waits until its stream's creation is durable. Released versions (0.2.0 to 0.2.2) are not affected.
- Fixed: an async commit waiting for admission could miss its wake when a charge returned at the same moment it queued (#645). Found by a loom model; not observed on hardware.
- Stall counters (ICR 0015, #64): `Metrics::wal_inline_syncs` and `file_growths`, `PagerStats::growths` and `growth_nanos`, and `WalCounters`.

### Metrics
- **`Pigeonhole::engine_metrics()` and `EngineMetrics` are documented public API** (ICR 0044). Every field is named and documented (unit, and whether it is a counter that starts at 0 at open and never resets, or a gauge). New: `EngineMetrics::commits(Durability) -> CommitStats` (count and p50/p99/p99.9 latency) and `cross_shard`. `EngineMetrics` was a hidden bench hook re-exporting the engine's `Metrics`; it is now the public crate's own struct, with tuple fields split into named ones (see [Upgrading](#upgrading-from-02x)).

### Defaults
Each of these changes behaviour on upgrade; [Upgrading from 0.2.x](#upgrading-from-02x) says what to set to keep the old one.
- **Engine-owned shard and compaction threads are pinned to CPUs of their own** (`Options::pin_threads`, D235): inside the opening thread's affinity set, one per physical core first. Opens never fail because of pinning: threads run unpinned on macOS, under a CPU quota narrower than the affinity set, or when too few CPUs are free, and several databases in one process pin to different CPUs. `EngineMetrics::{threads_started, threads_pinned, unpinned_reason}` report it. When the CPU set has room for the shard threads but not the compaction threads, the shards are pinned and only the compaction threads run unpinned.
- **One shard per physical core** the process may run on, not one per logical CPU (D220): SMT siblings count once, and a cgroup quota still caps it. On the reference machine (16 cores, 32 threads), 16 shards gave twice the durable group-commit throughput of 32. With pinning, shard `i` goes to the `i`-th physical core's first CPU.
- **The I/O backend is `IoBackend::Auto`** (D218): io_uring where the kernel offers it, the `pread` thread pool elsewhere; the open never fails over it.
- **The row cache is on, at 64 MiB** (D216, amending D201). A writer's caches default to 256 MiB of block cache plus 64 MiB of row cache, and about 6 MiB of per-row write watermarks zeroed at open; each write pays one atomic per row it touches. Reader processes are unchanged.
- **The group sync depth is 2 on Linux and 1 on macOS** (D221), and scans read 16 blocks ahead (D222). The measurement variables `PIGEONHOLE_GROUP_SYNC_DEPTH` and `PIGEONHOLE_READAHEAD` are gone.
- **Buffered commits spin briefly before parking** (D198, D253): 50 µs on the client (`Options::commit_spin`), and an engine-owned shard that handled a message polls 200 µs for the next one (`Options::shard_spin`, D198 amended 2026-10-19). On a Linux CI runner a buffered commit's median fell from 32.9 µs to 4.1 µs; the client's 50 µs covers a cross-shard commit's two rounds, which on the cross-shard mix gave +16% throughput and a 27% lower p50 than 15 µs. The shard's 200 µs wakes busy shards less: on the reference machine, shard parks fell from 0.02–0.42 to at most 0.075 per operation, a write p99.9 from 424 to 289 µs, and one-client ycsb-a rose 10–13%. Durable commits, idle databases and application-owned shards do not spin; `Duration::ZERO` turns either window off.
- **Engine-owned databases run flush and compaction on threads of their own** (D252): one per four shards, at least one and at most four (`Options::compaction_cores`). On a shard thread, each 500 µs flush or compaction slice held up the commits queued behind it; on the reference machine the change cut contended buffered ycsb-a's p99 from ~370 µs to ~45 µs and cross-shard commits' from ~550–890 µs to ~95–125 µs, with more throughput. Application-owned mode still starts no threads; its default stays 0.
  - With io_uring, these threads complete their own I/O on rings of their own, as shard threads do (#729). Through the backend's shared ring, every compaction read waited behind one reaper thread, and contended write loads fell to a few thousand ops/s with `Busy` after the write-stall timeout.
- **The `async` feature is on** (D17; see [Async front door](#async-front-door-42)).

### Bench and gate
- **The Phase 3 gate-window runbook** (#405): `crates/bench/baselines/phase3-gate/run-window.sh` runs every measurement the gate needs on the reference machine, resumable, with a `summary.md` of every #406 target; `gate-dry-run.yml` runs it small on a Linux runner. Steps include scaling, cold get (block cache at 1/64 of the table, D215), scan rate (`examples/scanrate.rs`), the row cache (`--row-cache`), `wal_pin_bytes` (#527) and the durable group commit at 4, 8 and 16 in flight (D226).
- **Gate judgments:**
  - engine scaling (≥ 0.8 × N) is judged up to one chiplet's physical cores, read from the L3 topology, and larger N is reported (D238);
  - the memtable lookup at 2^18 entries is accepted up to 354 ns, 5% above 337 (D239);
  - durable group commit is judged on 2M commits, and the scaling gate on at least 8 s per shard count (D219).
- **Reproducible runs:**
  - every engine settles after the load (a flush, then a bounded wait for quiet background work) before the warmup (D233), and `compare` notes pairs whose measured phases did different background work;
  - the warmup runs on the measured phase's own client threads until the tablet placement has gone 2 s without a change (D242);
  - `compare` judges only results of 10 s or more (or 2M group commits), and the gate runs `all` with `--min-secs 10` (D243);
  - `compare` fails a latency only past both its relative tolerance and an absolute floor: p50 ±20% or ±3 µs, p99 ±40% or ±6 µs, the floors scaling with `--tolerance` (D259). Throughput is judged as before, and p99.9 is still reported only. A one-thread p50 that moved 2.5 µs (+25%) had failed the gate's reproducibility check.
- **The D213 group-commit and scaling runs:** application-owned shards committing inline with 16 in flight (D204, D213), a fixed pre-split placement, threads pinned and reported unpinned beside them (D235), a run failed as skewed when one shard took more than 1.25/N of the commits (D223), waits on each shard's completion fd instead of spinning (p99 at 32 io_uring shards 1.3–3.5 → 0.29–0.36 ms), and a clean exit when a shard thread panics.
- **Contended cross-shard commits** (D246): `phdb-bench cross-shard-contention` (32 clients over 16 partitions, half the commits across 2–4 of them) against RocksDB's multi-key `WriteBatch`, in `all`, with Pigeonhole also run with tablet changes off and with packing off. Records carry the engine's cross-shard counters, and the gate judges wasted two-phase rounds per cross-shard commit, `Busy`, tablets on against off, and the cross-shard commit p99 at each durability (within 1.5× of RocksDB's batch p99; at most 2 ms at `Buffered` and 1 ms at `GroupSync`).
- **The gate's window trims the data file system before every step** (D258): a drive still mapping the terabytes earlier steps deleted had put the group-commit row in a slow mode. Each trim is logged, and `machine.json` records the namespace's mapped part. The bench's warm-up (D242) also waits out a pending balancer growth, and while fewer shards hold a tablet than the balancer's active count (D242's second amendment), so a measurement no longer starts inside a regrow after a packed load (#745, #751).
- **The gate's `contended` step** (D247): 16 client threads on the default options, runs of at least 60 s and at most 3× that, against RocksDB and SQLite at D108's buffered parity and at the default durability (`GroupSync` against fsync per write). Judged within 1.5×: ycsb-a/b/c/e, ycsb-f's atomic read-modify-write, sparse-wide, time-series, cross-shard-contention and counters. Reported: transfer, application-owned mode, the async API at 4 and 16 in flight, snapshot and durable-snapshot readers with a backup and a compaction beside the load, filtered scans, deletes and 16 KiB values. New workloads `counters`, `transfer`, `app-owned`, `adjacency-prefix`, `time-series-range` and `sparse-wide-deletes` (not in `all`), and options `--durability buffered|sync|group-sync|default` (load buffered, then switch), `--async N`, `--riders` and `--max-secs`. The summary reports each contended workload's p99 per operation type against the same type in RocksDB and SQLite, beside the judged p99 over every operation (D261). ycsb-f's read-modify-write is now atomic across client threads in every store, so it runs at any `--threads`; after a switch to a durable level, the warmup waits 5 s without a placement change (at most 60 s).
- The window's `ycsb-a-shards` step runs the shard spin at 0, 100 and 500 µs beside the default 200 µs.
- New options: `--min-secs`, `--inline-ops`, `--in-flight`, `--row-cache`, `--offered-rate`, `--shard-spin`. Records carry each run's stalls, flushes, compactions, visibility waits, park and wake counts, per-shard busy time and row-cache counts. Results from before the settle, warmup and inline-wait changes aren't comparable.

### Known issues
The owner released 0.3.0 with these gaps against the Phase 3 gate; each is a Phase 4 issue under [#695](https://github.com/CodingAnarchy/pigeonhole/issues/695).

Under contention (16 client threads on the default options):

- **Short scans** (ycsb-e: scans of 1–100 rows) trail RocksDB by 3.9× in throughput at buffered and 3.3× at the default durability (scan p99 1.58 ms against RocksDB's 276 µs at buffered). At one client they are within 1.5×, so the gap opens with concurrency ([#712](https://github.com/CodingAnarchy/pigeonhole/issues/712)).
- **Counters:** counter reads have a p99 of 10.8 ms at buffered and 17.2 ms at the default durability at 16 clients (the whole mix's p99 is 82× SQLite's upsert at buffered and 52× at the default) ([#713](https://github.com/CodingAnarchy/pigeonhole/issues/713)).
- **Transactions on hot rows:** `transfer` (optimistic transactions moving units between Zipfian accounts) varies 4.7–14K ops/s across gates at buffered, 38–106× behind RocksDB, and runs 8.8× behind it at the default durability, with 1.2 and 1.8 conflicts per transfer on the release gate ([#708](https://github.com/CodingAnarchy/pigeonhole/issues/708)).
- **Cross-shard commits:** at the default durability the mix's p99 trails SQLite's single-writer transactions by 2.29×, and the cross-shard commits' own by 2.05× (255 against 124 µs); packing gathers mostly cross-shard loads onto fewer shards than they need ([#707](https://github.com/CodingAnarchy/pigeonhole/issues/707)).
- **The async API at 16 in flight per client** runs at 0.41× the synchronous throughput at buffered (473K ops/s, p99 11 ms; [#749](https://github.com/CodingAnarchy/pigeonhole/issues/749), [#709](https://github.com/CodingAnarchy/pigeonhole/issues/709)).
- **Application-owned mode on the defaults** runs at 0.20× the pre-split scaling run at buffered ([#710](https://github.com/CodingAnarchy/pigeonhole/issues/710)).
- **time-series-range** trails RocksDB (1.07× at buffered, 1.03× at the default) where time-series-ttl leads it (0.31×) ([#711](https://github.com/CodingAnarchy/pigeonhole/issues/711)).
- **Cross-shard commits after packing regrows a store:** a cross-shard store whose write set grows after D257 packed it (pack, then regrow) runs at about 0.7× the packing-off throughput for the rest of the session, with p99.9 near 1 ms; reopening the store, or `Options::tablet_packing(false)` (the bench's `--no-packing`) for such loads, avoids it ([#767](https://github.com/CodingAnarchy/pigeonhole/issues/767)). After the regrow the shards' flushes fall out of step, and each flush still holds a shard for a few milliseconds while it scans and settles cross-shard share reports, so some shard is nearly always stalled. #761, #762 and #764 (which bounds the WAL checkpoint's pops, [#727](https://github.com/CodingAnarchy/pigeonhole/issues/727)) narrow it; moving that work off the shard thread is Phase 4 ([#724](https://github.com/CodingAnarchy/pigeonhole/issues/724)). The gate's own cross-shard rows do not pack during their load: tablets on ran at 1.00–1.01× packing off in `all` and 0.97× contended at buffered, where Pigeonhole still trails RocksDB by 1.34× in throughput with a 2.95× p99 (113 against 38 µs).
- **Read-modify-write at the default durability:** ycsb-f's p99 is 2.04× SQLite's. With fewer commits in flight than shards, `GroupSync` has nothing to batch, so each commit pays its own fsync ([#755](https://github.com/CodingAnarchy/pigeonhole/issues/755)).
- **Reads beside writes:** row-read and scan p99 run 1.8–2.2× SQLite's while other clients write (ycsb-a, ycsb-f, sparse-wide and time-series-ttl) ([#759](https://github.com/CodingAnarchy/pigeonhole/issues/759)).
- **sparse-wide puts at buffered:** the put p99 is about 30× RocksDB's (498 against 17 µs) ([#760](https://github.com/CodingAnarchy/pigeonhole/issues/760)).

Run to run:

- The gate's two runs of `all` differed past D243's tolerance on group-commit at 16 clients (throughput −21%, p99 +49%: run 1 was a fast outlier) ([#768](https://github.com/CodingAnarchy/pigeonhole/issues/768)). RocksDB's one-client adjacency throughput also moved −20.1%, which is RocksDB's own variance.

Placement and tails:

- The write-skew mover can stop with tablets still to move: a hot shard keeps most of the tablets while active shards sit empty, until the load changes ([#735](https://github.com/CodingAnarchy/pigeonhole/issues/735)).
- With the store spread over every shard, a commit that lands on a shard that has just parked pays its wakeup: the put p99.9 is about 110 µs at 16 clients, against about 85 µs when the same load is packed onto fewer shards ([#738](https://github.com/CodingAnarchy/pigeonhole/issues/738)).
- A store packed by a light load (one loader) regrows one tablet move per dwell when many clients arrive: the regrow takes several seconds, and writes during it see a p99.9 of about 420 µs against about 110 µs on a spread store ([#744](https://github.com/CodingAnarchy/pigeonhole/issues/744)).

### Upgrading from 0.2.x
- **Files.** The file format is unchanged (version 2): files written by 0.2.x open and read as before. Keep a backup from before the upgrade if you may need to go back.
- **Reader processes.** The shared-memory layout is version 2 (FORMAT §11.2). Writer and reader processes must run builds with the same layout: **stop reader processes before upgrading the writer.** A new writer fails to open with `ShmVersionMismatch` while readers of an older build are still attached, and an old reader can't attach to a new writer.
- **Visibility.** Readers now see a commit once it is applied, before its fsync (D227). If a reader must not act on a commit a power loss could remove (deriving a write on another shard from what it read, persisting a cursor, taking a backup), read from `durable_snapshot()` and back up with `backup_durable`. A commit's own call returns when it did before.
- **Errors.**
  - Handle `ErrorCode::OutcomeUnknown` (28) on commits: the commit may or may not have happened; reopen and read it back, or write it again if it is idempotent. `ErrorCode` and `Error` are `#[non_exhaustive]`, so existing matches compile, but a catch-all arm that treated every failure as "not written" is now wrong for this code.
  - `Closed` now always means not committed. After any shard's death, every new commit fails with `Closed` (healthy shards included) until you close and reopen; poll `Pigeonhole::is_failed()` from a health endpoint or supervisor to learn of it without a commit.
  - **`Conflict`** on a cross-shard transaction now means a real read-write conflict (D249): code that retried every `Conflict` still works and retries less. Under contention the engine refuses and retries cross-shard PREPAREs internally (D244, D245, D249), and a commit that can't get through by `write_stall_timeout` gets `Busy`.
  - **`Busy`:** the write-stall timeout is per waiting write (D240), cross-shard commits retry tablet changes until that timeout (D241), and the L0 stall starts at 8 files, not 4 (D234). A bulk load that used to fail with `Busy` should now finish; a write that does get `Busy` really waited `write_stall_timeout`. Code that matched the old message text needs the new one.
- **Threads and placement.**
  - Threads are pinned by default (D235). Several processes with Pigeonhole on one host should each get their own CPUs (an affinity mask or a cpuset) or open with `Options::pin_threads(false)`.
  - The default shard count is the physical cores, so an SMT machine gets half the shards it did. `Options::shards(n)` sets it.
  - Tablet packing (D217, D257) gathers a store with few commits in flight onto fewer shards; `Options::tablet_packing(false)` keeps 0.2's placement. Balancer moves are slower to start (D214, D224).
  - Engine-owned databases start one flush and compaction thread per four shards, one to four (D252); `Options::compaction_cores(0)` runs flush and compaction on the shard threads as 0.2 did.
- **Memory and CPU.** A writer uses about 70 MiB more by default (the 64 MiB row cache and its per-row watermarks; `Options::row_cache(0)` turns it off), and io_uring rings register up to 1 MiB each of locked memory within `RLIMIT_MEMLOCK`. Buffered commits spin up to 50 µs on the client, and engine-owned shards poll up to 200 µs, before parking; on battery-powered or CPU-constrained hosts set `Options::commit_spin(Duration::ZERO)` and `shard_spin(Duration::ZERO)`.
- **I/O backend.** Linux uses io_uring where the kernel offers it (D218). `Options::io_backend(IoBackend::Pread)` keeps 0.2's behaviour.
- **Application-owned mode** (`Shard::run_once`):
  - **Poll your futures after every `run_once` call,** not only once it returns `false` (D237). A call that settles a commit the loop awaits returns `true` early, with background work still to run; a loop that polls only when idle still works but loses the latency gain. Wait with `Shard::wait(timeout)` when `run_once` returns `false`, and give the futures the loop polls `shard.waker()`; the [async guide](docs/guide/async.md) has the loop.
  - With io_uring the engine starts no I/O threads: use `Shard::wait`, or wait on `Shard::io_fd` in your own event loop (D202). A loop that takes neither keeps polling while I/O is in flight.
  - Call `Shard::release()` before handing a shard to another thread.
- **Async.** The `async` feature is on by default and adds the `futures-core` dependency; `default-features = false` drops both. An async commit future dropped while it waits for room (D210) writes nothing: await it, or use `WriteBatch::commit_with_ticket`, which always submits.
- **Measurement variables.** `PIGEONHOLE_GROUP_SYNC_DEPTH` and `PIGEONHOLE_READAHEAD` are gone; the settled values are built in (D221, D222).
- **API.** No breaking API change: `cargo semver-checks` against 0.2.2 passes for every published crate. The changes are additions, and the behaviour changes above.
- **Metrics.** If you read the hidden `engine_metrics()` in 0.2, its tuple fields are now named (ICR 0044): for example `stalls.0`/`.1` became `write_stalls`/`write_stall_nanos`, `block_cache.0`/`.1` became `block_cache_hits`/`block_cache_misses`, `pinned_threads` became `threads_pinned`/`threads_started`, and per-durability commit counts and latencies come from `commits(Durability)`. ICR 0044 lists every rename.

## [0.2.3] - 2026-10-20
A fix for a lost write under concurrent cross-shard and single-shard commits. **Upgrade recommended** for every 0.2.x user whose writes span shards. The file format is unchanged, and files written by 0.2.0 to 0.2.2 open as before. Every published crate moves to 0.2.3 together.

**Known issue (#655, also in 0.2.2):** a cross-shard commit that finds a participant's memtable arena full waits for room while holding its sequence number, and that participant's flush waits for the same sequence number to become visible. With a real clock the wait ends at the write-stall timeout (`Options::write_stall_timeout`, 30 s by default): the commit, and writes queued behind it on that shard, get `Busy` and can be retried. It needs a full arena, so a larger `Options::memtable_budget` makes it rarer. 0.3.0 refuses such a commit and retries it once room frees, instead of letting it wait (D245).

### Fixed
- **A write could be lost behind an earlier cross-shard commit to the same row** (#653, D244, D245).
  - **When:** a commit wrote rows on more than one shard, and another thread wrote the same rows on one of those shards, without explicit timestamps, just after it. More likely with many threads and busy shards. Tablet changes on or off.
  - **What happened:** the shard could give the later single-shard write a default timestamp below the cross-shard commit's. Reads then returned the cross-shard commit's older value, and the later write was lost.
  - **The fix:** the coordinating shard raises every participant's timestamp floor before it takes the commit's sequence number, so later writes there stamp above the commit (D245). A participant also refuses a commit whose timestamp would land out of order with writes it has already made, and the commit is retried with a fresh timestamp (D244).
  - **Side effect:** a cross-shard commit refused this way is retried internally. Like one refused for a tablet change, it gets `Busy` after 16 refusals or the write-stall timeout. That is rare, since the floor raise above prevents almost every refusal.

## [0.2.2] - 2026-10-12
Fixes to closing a database after cross-shard commits. **Upgrade recommended** for every 0.2.x user whose writes span shards. The file format is unchanged, and files written by 0.2.0 and 0.2.1 open as before. Every published crate moves to 0.2.2 together.

### Fixed
- **Closing the database could hang forever after concurrent cross-shard commits** (#585, D225).
  - **When:** two commits that each wrote rows on more than one shard were in flight together, and each was coordinated by a shard the other wrote to. Likelier with many shards and many threads writing at once.
  - **What happened:** each shard's WAL checkpoint waited for the other's, so neither could move. `close` waited for them and never returned. While running, the WAL stopped being trimmed past those commits. With many such commits in flight, a shard thread could instead overflow its stack during the close and abort the process.
  - **The fix:** a shard drops a cross-shard commit's record from its WAL once every shard's part of the commit is written to the file, without waiting for the coordinating shard's checkpoint (D225).
- **Closing the database could hang forever after a crash during cross-shard commits** (#591). The reopen recovered correctly, but a commit the recovery had correctly discarded was later treated as undecided, and the close waited for it.
- **Closing the database could hang forever after a tablet move** (#597): a shard was not told when another shard wrote its moved data to the file, so a commit never completed its bookkeeping.

## [0.2.1] - 2026-10-11
A fix to WAL crash recovery. **Upgrade recommended** for every 0.2.0 user. The file format is unchanged, and files written by 0.2.0 open as before. Every published crate moves to 0.2.1 together.

### Fixed
- **Records the WAL had lost could come back after a later recovery** (#508, D209).
  - **When:** a power loss (not a process crash) while a WAL segment was starting in a reused slot. The disk had to keep part of that write (the first records) and lose the rest (the segment's header). The database then had to reopen, write little or nothing more to that WAL stream, and recover again later.
  - **What happened:** recovery correctly ignored those records the first time. But the reopened stream reused the lost header's numbering in the same slot, so at the next recovery the old records read as new ones.
  - **Effect:** writes that a power loss should have discarded could reappear. Their sequence numbers could also be reused by newer commits, mixing old and new data in recovery. The records that come back are only ever ones that were never synced.
  - **The fix:** recovery now starts a reopened stream three numbers above the largest it saw (FORMAT §10.1). Nothing reads or writes differently otherwise.

## [0.2.0] - 2026-10-09
The **Phase 2 wide-column model**: counter families, large values and blob separation, per-family compaction styles and zstd, a file at rest near its live size, and the read- and write-path work that met the Phase 2 gate as amended by [D193](docs/design/decisions/phase-2.md#d193). Counters change in a breaking way, and the file format is version 2; see [Migrating from 0.1.0](#migrating-from-010). Every published crate moves to 0.2.0 together.

### Added
- **Counter families** (D179, D186, D187; #274). `Family::counter()` declares one, after Bigtable's aggregate families:
  - `incr` writes at one fixed timestamp (0), so a counter is one cell however often it is incremented: increments combine at read time and in compaction.
  - `incr_at(family, qualifier, ts, delta)` adds to the bucket at `ts` (hourly or daily totals; each bucket is a version). `put_i64` sets the counter and `put_i64_at` a bucket; later increments add to them.
  - Writes of one counter in one mutation or batch apply in order (D186, #295): `incr(c, 1).incr(c, 2)` adds 3, and `put_i64(c, 5).incr(c, 1)` leaves 6. Other families keep D34 (the last write of a cell in a commit wins).
  - Only `i64` values are accepted: `put`, `put_at`, `put_f64` and untyped `merge` operands fail with `InvalidArgument`.
  - A delete hides only what was written before it, so an `incr` after `delete_column` or `delete_row` starts the counter from 0. Deletes are purged by a bottommost compaction (D187).
  - A TTL expires each bucket. With a TTL the fixed timestamp would expire at once, so there `incr` and `put_i64` without a timestamp fail with `InvalidArgument`. `max_versions` limits reads; compaction keeps older buckets, so bound storage with a TTL.
- **Blob separation and blob GC** (#33, D180, D184). Values above a family's `blob_threshold` (default 4096 bytes) move to blob files when flushed or compacted. Blob GC rewrites a blob file once it is about half garbage, following the references each SST records. Value filters test a separated value like an inline one. `backup` copies the separated values its snapshot references (D182), and `shrink` relocates blob extents too (D185).
- **Values up to 4 GiB − 2 bytes** (D188, #230). A put longer than the inline limit (the smallest of the WAL segment payload, 64 MiB and half a shard's memtable arena) is written to a blob file when it is committed, so only a pointer goes through the WAL and the memtable. Such a put costs one extra manifest commit, with its file sync, even under `Durability::None`. `ValueTooLarge` now means a value above 4 GiB − 2, or a merge operand above the inline limit.
- **Per-family compaction styles** (D168; #31, #32, #44). `Compaction::Tiered` (universal, for write-heavy families) and `Compaction::FifoByTime` (drops whole SSTs once their newest timestamp passes the TTL, with no rewrite) are accepted at table creation. `FifoByTime` expiry runs on a timer, so an idle family drops expired files on time (#232). See [Compaction styles](docs/guide/concepts.md#compaction-styles).
- **zstd block compression** (D175, #44). `Family::zstd(level)` is accepted at table creation and stores blocks as zstd frames at the family's level.
- **The FUSE opt-in** (D173, #299). `Options::allow_fuse(true)` and `ReaderOptions::allow_fuse(true)` accept a database on a local FUSE mount the user trusts (ntfs-3g, gocryptfs). FUSE is refused by default, and network and cluster filesystems are refused either way. `pigeonhole-io` adds `File::locality` and `Locality`.
- `Options::write_stall_timeout(Duration)`: how long a stalled write, `flush` or `compact` waits before `Busy` (default 30 s, as before) (#210).
- `pigeonhole-engine`: `Engine::tablet_refusals()`, the tablet splits and moves refused for lack of room (#122).

### Changed
- **Breaking: counters need a counter family** (D179). `Family::default()` no longer carries the `pigeonhole.i64_add` operator, and `incr` on a family that is not a counter family fails at commit with `ErrorCode::InvalidArgument`. Families in files written by 0.1.0 keep 0.1.0 behavior (see Migrating).
- **Breaking: `#[non_exhaustive]` on structs that may grow** (#296), so a later field is not breaking: `FamilyOptions` (`pigeonhole-format`, re-exported by `pigeonhole-engine`), `ModelFamily` and `ModelPurge` (`pigeonhole-sim`), and the result types `Metrics`, `ShardStats`, `TableInfo`, `FamilyInfo`, `CompactionRecord` (engine), `CompactionOutput` (compaction) and `PagerStats` (pager). Each field has a builder setter. The public `pigeonhole` API is unaffected (`Family` and `Options` are builders already).
- **Breaking, lower-level crates:** `pigeonhole-engine`, `pigeonhole-format`, `pigeonhole-compaction` and `pigeonhole-sim` add `FamilyOptions::kind` (`FamilyKind::{Standard, Counter}`), `WriteBatch::merge_at`, `COUNTER_TS`, `ResolveOptions::counter`, `GcPolicy::other_sources`, and the model's `ModelFamily::counter`, `ModelOp::Incr::ts` and `ModelError::CounterWrite`.
- **On-disk format version 2** (FORMAT §12). This release reads 0.1.0 files, but a file it has written can't be opened by 0.1.0.
- **Flushes purge overwritten versions** (D191, #287). A flush runs its memtable through compaction's GC: it drops what a non-bottommost compaction could (expired cells, cells hidden by a delete at every live snapshot), and the versions beyond `max_versions` when no other source of the family's tablet holds a delete. Live snapshots read exactly what they did before. Delete markers are still purged only by a bottommost compaction.
- **A file at rest stays near its live size** (D183, #185). Compaction cuts its level outputs into power-of-two pieces, so after `compact()` and `shrink()` a file above 5 MiB is 1.05–1.16× its live data, where it was 2–4×. `shrink` can also move a large extent down when small extents fragment every hole below it (D190, #314). No migration: each compaction rewrites its outputs in the new shape.
- The write stall follows L0 depth only; deeper levels and tiered space amplification no longer pace writers (D119).
- Custom merge operators now work. In 0.1.0, operators registered with `Options::merge_operator` and `ReaderOptions::merge_operator` never reached the engine (#43, #253). A handle opened with `allow_unregistered_merge_operators(true)` is now read-only, as documented: writes, transactions and table changes fail with `ReadOnly`.

### Fixed
- A write with an explicit timestamp older than a running bottommost compaction's inputs could change a read when the compaction installed, with no write in between: a cell delete exposed an older version the compaction then purged, or a put below a purged delete appeared. The compaction now runs under a guard, as a flush's purge does (D192, #316): such a write voids it before it installs (it compacts again), or waits while it installs. After three voids in a row, the slot compacts once without that purge, so a backfill written newest to oldest can't keep it from finishing.
- With tablet changes off, a shard's memtable arena is sized for the table and family slots it holds, as with them on (D189, #283). A memtable budget under 16 MiB used to serve only 16 slots per shard, and more stalled writes until `Busy`.
- A database on NFS without working locks fails to open with `NetworkFilesystem` instead of an I/O error about locks, and FUSE and GPFS mounts are refused as network filesystems (D173, #147).
- `backup` holds the snapshot's memtables only while it copies them, not for its whole merge, so writers no longer wait for arena room during a long backup (#262).
- Space a moment-old view kept retired is reclaimed as soon as that view goes, not at the next manifest commit, so `shrink` on an idle database gives it back (#337).

### Performance
The Phase 2 gate ([D193](docs/design/decisions/phase-2.md#d193)) is met: on `phdb-bench sparse-wide --scale full` (10 shards, 64 MiB memtables, 256 MiB cache, one client thread; official runs 5–6 on a quiet 10-core Apple M5), Pigeonhole beats hand-keyed RocksDB on every measure and matches or beats SQLite EAV on throughput, get and put p99, and p99.9.

| Store | ops/s | p99 µs | p99.9 µs | get p99 | put p99 | row-read p99 | scan p99 |
|---|--:|--:|--:|--:|--:|--:|--:|
| Pigeonhole | 28.7K / 30.4K | 389 / 395 | 528 / 541 | 98 / 11 | 17 / 17 | 455 / 459 | 489 / 496 |
| SQLite EAV | 27.1K / 29.8K | 245 / 250 | 1,040 / 938 | 156 / 152 | 178 / 172 | 222 / 231 | 293 / 307 |
| RocksDB | 20.4K / 20.4K | 709 / 791 | 1,012 / 1,196 | 161 / 155 | 9 / 9 | 840 / 963 | 881 / 1,016 |

- **Documented gap** ([#387](https://github.com/CodingAnarchy/pigeonhole/issues/387), Phase 3): reads of very wide, heavily overwritten rows have a p99 about 2× SQLite EAV's for row reads and 1.6× for scans. An overwrite adds a version, and those reads step over the superseded versions until compaction removes them; a compacted hot row costs about the same per cell as SQLite. The guide's [Wide, overwritten rows](docs/guide/data-modeling.md#wide-overwritten-rows) says how to keep it down.
- **The work behind it** (#287, #46, #320): commits make a small constant number of allocations; point gets, row reads and scans reuse their thread's resolver in place, and a scan reads each level below 0 through one lazy cursor, opening only the SSTs it reaches; flush-time version GC; and many cheaper steps in the write path, the merge, the resolver and block decoding. **D193's floors** keep what Phase 2 reached: CI's instruction counts fail a change that makes any measured read or write shape worse than its per-change threshold or puts it above its absolute ceiling (`crates/bench/baselines/instruction-ceilings.txt`), and every later official gate run, including the one before each release, is compared with the committed Phase 2 baseline (`crates/bench/baselines/phase2-gate`).

### Migrating from 0.1.0
- **Files.** Files written by 0.1.0 open and read as before. Files written by 0.2.0 use format version 2 and can't be opened by 0.1.0, so keep a backup from before the upgrade if you may need to downgrade.
- **Counters.** Families in 0.1.0 files store `pigeonhole.i64_add` without a kind (the new `kind` byte reads as `Standard` when absent) and keep 0.1.0 behavior: `incr` still works there, at the commit timestamp, with runs of increments folded across timestamps when read (D41), and `put` of bytes still works. New code that declares a family with `Family::default()` and calls `incr` on it fails with `InvalidArgument`: declare it with `Family::counter()`. An existing family keeps its stored kind (declaring it again with other options changes nothing), so to move counters, add a counter family and copy each counter: read it with `get`, write the value with `put_i64` (or `put_i64_at` for a dated bucket) into the new family, then point increments there. For a new family with 0.1.0 behavior, declare `Family::default().merge_operator("pigeonhole.i64_add")`. Per-period counters kept as one qualifier per period can stay as they are, or become buckets of one column with `incr_at`.
- **`FamilyOptions` and the model types.** Code that builds `FamilyOptions`, `ModelFamily` or `ModelPurge` with a struct literal no longer compiles outside its crate. Start from the default and use the setters, one per field: `FamilyOptions::default().max_versions(1).merge_operator("pigeonhole.i64_add")` instead of `FamilyOptions { max_versions: 1, merge_operator: "pigeonhole.i64_add".into(), ..FamilyOptions::default() }`; `ModelFamily::new("f").counter(true)`; `ModelPurge::new("t", "f").snapshots(s).now(now).min_ts_above(ts).max_seqno(n)`. Reading and assigning fields still works.
- **FUSE.** A database on a FUSE filesystem (ntfs-3g, or an encrypted home directory such as gocryptfs) now fails to open with `NetworkFilesystem` (#147). If the mount is local and you trust it, open with `Options::allow_fuse(true)` (and `ReaderOptions::allow_fuse(true)` in reader processes); never for network-backed FUSE such as sshfs or s3fs.

## [0.1.0] - 2026-10-08
The first release: the **Phase 1 core engine** of an embedded, single-file, wide-column store ([release notes](https://github.com/CodingAnarchy/pigeonhole/releases/tag/v0.1.0)).

### Added
- One-file embedded database (`.phdb`, plus WAL sidecars and a shared-memory region while open); `Options::default()` is valid.
- Thread-per-core shards with per-shard WAL streams and group commit; durability levels `None`, `Buffered`, `GroupSync` and `Sync`.
- All-or-nothing cross-shard commits (two-phase commit), a global visibility watermark and MVCC snapshots.
- Tablets that split, merge and move between shards (on by default).
- Per-family LSM: shared-memory memtable arenas, SSTs, leveled compaction, HBase-style delete and GC semantics, counters (`incr`), merge operators and TTL.
- Reader processes that attach through shared memory; snapshots expire cleanly across a writer restart (`SnapshotExpired`).
- Maintenance: `flush`, `compact`, `backup` and `shrink`.
- Cheap opens: about 14 ms and well under 1 MiB written for a small database, whatever the shard count.
- A flat, stable `ErrorCode`, including `Busy` (retryable stall), `BatchTooLarge`, `ShmUnavailable` and `WouldDeadlock`.
- The user guide, an agent reference and the design decisions log.

### Testing
- Deterministic simulation with fault injection, process crashes and power loss, checked against a reference model with a record-level recovery oracle.
- Seed sweeps of 1-300 on every suite, Miri on the `unsafe` crates, loom on the concurrent ones, and CI on Linux, macOS and Windows.

### Known limits
- Write throughput does not yet scale with shard count (#154, Phase 3).
- Open latency is about 14 ms against the 5 ms goal (#158, Phase 3).
- The file at rest can be 2-4x live data (#185, Phase 2).
- Application-owned mode still runs the default I/O backend's 2-16 I/O threads (Phase 3).
- `pigeonhole-cli` (`phdb`) is a placeholder until Phase 4.
