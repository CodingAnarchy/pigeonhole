### Added
- **Clusters: `phdb serve --cluster DIR --node-id ID` and `phdb cluster`** (D317, ICR 0117, #1482): a table's rows in static partitions across nodes, each partition a database that one node serves. A cluster node doesn't serve the IVF and full-text indexes, agent memory or `/mcp` yet (#1722).
  - **The map:** nodes keep the cluster's partition map, the schema included, and distribute it. One node writes it, the one with the smallest id: schema changes and `phdb cluster set-map` go through it, and `set-map --force` sets a map at another node when the writer is down. `phdb cluster init-partition` stamps a partition file; `set-map`, `show-map` and `status` set, show and check the map, and `status` shows each partition's state. A new `cluster` token scope is for node-to-node calls, and table names starting with `__phdb_` are refused and hidden from listings.
  - **Data through any node:** a single-row read or write, or a one-partition batch, is served or forwarded to its partition's node (`Cluster.Forward`). A batch across partitions is refused with `CrossPartition` before anything is written. Scans and multi-gets (`Cluster.ForwardScan`), `Vectors.Nearest` and `Graph.Traverse` fan out across a table's partitions and return what one database holding every partition would: the exact top `k`, and traversals with the same hops, parents and stats. A page's `next` resumes through any node. `allow_partial` skips a partition that can't be reached and names its key range in `missing`; without it, the read fails with `PartitionUnavailable`. A fanned-out read counts its partitions' pages against `--inflight-bytes` on the node it entered, and `--fanout-forwards` (8) caps the forwards one read runs at once.
  - **Transactions and snapshots** live on their partition's node, named by `route` in `Begin` or `Snapshots.Open` (required on a cluster). Their ids name the partition, so any node routes the calls on them. A row outside the partition is refused with `CrossPartition`.
  - **Schema:** `Schema.CreateTable` takes a `placement`. `CreateTable`, `DropTable`, `ListTables`, `DescribeTable` and `GET /v1/tables` work through any node. Each node makes its partitions' files follow the map; it leaves hand-made tables alone and reports them in `Cluster.Status`.
  - **Change feeds:** `Feed.Subscribe` through any node follows every partition the subscription's tables (and prefix) cover, merged into one stream, each partition's commits in order and each event naming its `partition`. Tokens come as checkpoints (`checkpoint_every`), about 150 bytes of token per event on average. A resume from the last one may repeat the commits after it, which a client drops by `(partition, seqno)` or names in `skip_through`. `allow_partial` keeps a stream going without an unreachable partition, reported in `PartitionState` events, and picks it up again where it left off. A subscriber that stops reading is ended after `--stream-idle-ms`. A cluster node takes `--change-feed` for its partitions.
  - **Several partitions a node:** a node serves every partition the map gives it. `--shards` and the new `--compaction-threads` are the node's totals, split across its partitions. `--engine-memory` sets the engine's memtables, block cache and row cache; on a cluster node it's the node's total, after the map's per-partition `memory_bytes`. Each partition's thread placement and memory are on the startup line, and `/metrics` and `Admin.Metrics` label each partition's series `pigeonhole_partition`.
  - **Fencing and relocation:** `phdb cluster fence`, `unfence`, `close`, `relocate --to ID` and `drop-partition`. A fenced partition's writes answer the new code `Fenced` through every node, and a fence is kept across a restart; a restarted node keeps its partitions fenced until a peer's map confirms them. `close` makes a partition's files final, and `Cluster.Status` lists them with SHA-256. A node takes a partition's files in through `Admin.PartitionUpload`, resumable through `Admin.PartitionUploadStatus` (`--max-uploads` at once), and `relocate` installs them on the new node and moves the partition there. A node opens a partition the map gives it while it serves.
  - **Moves:** `phdb cluster move P --to ID [--drop-source] [--timeout SECS]` moves a partition with its files copied whole. It fences and closes the partition, copies every file (`Admin.BackupDownload`'s `fenced_file`), checks the installed set against the closed one by SHA-256, then sets the map and waits for the new node to serve it. A rerun resumes a move that stopped, and `--drop-source` moves the old node's files aside once the copy checks out. `--timeout` gives up a wait for a node after SECS, naming the step and the node's last status for the partition. `phdb cluster relocate --copy` marks a relocation done by hand as such a copy.
  - **Feed history across moves:** the map records each partition's `history_epoch`. A move, or a `relocate --copy`, keeps it, so change-feed tokens from before resume after it. A `relocate` without `--copy`, a promotion, a restore, or a `set-map --force` that raises the partition's epoch starts a new history, and earlier tokens answer `FeedExpired`. A forced map is refused if it lowers an epoch, or moves a partition without raising its epoch, against any node's map it reaches; its report names the nodes it couldn't reach as `unchecked`.
  - **Backup and restore:** `phdb cluster backup DIR --node URL` backs up every partition, each through the node that holds it, with the map, into one directory (`map.json` and `manifest.json` describe the set). Each partition's copy is checked against the map and is a consistent snapshot of its own; the set is not one point in time across partitions. A backup during which a table is dropped and created again under its name fails. A cluster node's `Admin.Backup` and `BackupDownload` take the `partition` to back up, and cluster nodes accept `--backup-dir`. `phdb cluster restore DIR --node URL` puts a backup back: each copy is checked against the manifest, uploaded to the node the backup's map (or `--map`) gives it and installed there at a new epoch; then the backup's map is set by the forced path, its tables exactly as the backup has them, and each partition is unfenced once it's open. Fence every partition first, and close each on the node it's restored to; writes since the backup are lost. `--cluster-id` restores under another cluster id, `--old-unreachable` skips the check on a node that's down, and `--parallel N` uploads that many at once.
  - **New error codes:** `WrongPartition`, `CrossPartition`, `PartitionUnavailable` and `Fenced`.
