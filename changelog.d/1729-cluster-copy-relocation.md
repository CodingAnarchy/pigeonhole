### Added
- `phdb serve --cluster`: a partition relocated by copying its files keeps its history, so change-feed tokens from before the move still resume after it (D317 ticket 6, ICR 0117). The map records each partition's `history_epoch`, derived when the map is set: a relocation by copy (`SetMapRequest.copies`) keeps it, and a promotion or a restore starts a new one, whose earlier tokens answer `FeedExpired`. A forced map (`set-map --force`) restarts the history of each partition whose epoch it raises. It's refused if it lowers an epoch, or moves a partition without raising its epoch, against the receiving node's map or any node's that `set-map --force` reaches. The report names the nodes it couldn't reach as `unchecked`.
- `Admin.BackupDownload`'s `fenced_file`: on a cluster node, one file of a partition closed there after a fence (`""` for the main file), sent as it lies with its SHA-256, for a relocation by copy.
- `phdb cluster move P --to ID [--drop-source]`: moves a partition with its files copied whole. It fences and closes the partition, copies every file, checks the installed set against the closed one by SHA-256, then sets the map and waits for the new node to serve it. Change-feed tokens from before the move resume after it, a rerun resumes a move that stopped, and `--drop-source` moves the old node's files aside once the copy checks out.
- `phdb cluster relocate --copy`: marks a relocation as a copy of the partition's files, so its feed history carries over.
