### Added
- **`phdb cluster replay-tail P` replays an old owner's unreplicated tail into a cluster partition's new owner** (#2148, D336). After a failover or promote that left the tail PENDING, and once the old node has closed P (`phdb cluster close P`), each commit the old owner made past the fork point becomes one new commit on the new owner, with its cells' timestamps kept and a mark in the same commit, so a stop at any point resumes with nothing applied twice. `--dry-run` reports what it would do; `--discard` gives the tail up. Commits to tables dropped since, rows the partition no longer holds, and catalog changes are skipped; writes to an index's or a memory store's tables are refused and reported. A transaction's share across partitions is replayed once its home's decision row says committed (asked read-only). The tail is set DONE only by the replay, through the map's writer, which asks the owner first. While a tail is PENDING, no map places the partition on its old node, and the old node refuses to install over its file. Replayed commits carry `FeedEvent.replayed`, and `/metrics` counts them (`pigeonhole_cluster_tail_replay_commits_total`).
