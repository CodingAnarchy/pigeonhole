# 0051: `put_f64_at` on `RowMutation` and `WriteBatch`

**Status:** Approved (owner, via the coordinator, 2026-10-21; #692). Additive.

## Change

In `pigeonhole`:
- `RowMutation::put_f64_at(self, family: &str, qualifier: &[u8], ts: u64, value: f64) -> Self`
- `WriteBatch::put_f64_at(&mut self, table: &Table, row: &[u8], family: &str, qualifier: &[u8], ts: u64, value: f64) -> &mut Self`

Each stores a typed `f64` at an explicit timestamp, as `put_i64_at` does for `i64`. They use the same engine call as `put_f64`, with `Some(ts)` in place of the commit timestamp. Nothing below the public crate changes.

## Why

Every other typed put has an `_at` form: `put_at`, `put_i64_at`, and `incr_at` for counters. `put_f64` had none, so an `f64` cell couldn't be written at a chosen timestamp. That rules out event-time writes, and it rules out a `phdb load` that keeps a dumped cell's timestamp (#692, PR 4). Without it, PR 4 would have to load `f64` cells at the commit time and report them.

## Callers

- `pigeonhole`: `write.rs` (the two methods) and `tests/api.rs` (`put_f64_at_keeps_its_timestamp`: both forms, versions and the latest read).
- `pigeonhole-cli`: `phdb load` (#692, PR 4).
- Docs: the agent reference and the changelog.
